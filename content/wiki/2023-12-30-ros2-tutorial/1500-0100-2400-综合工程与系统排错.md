## 示例 1：从干净终端运行

```bash
source /opt/ros/humble/setup.bash
cd ~/ros2_control_humble_ws
colcon build --symlink-install --packages-select learn_control_hardware learn_position_controller
source install/setup.bash
ros2 pkg prefix learn_control_hardware
ros2 pkg prefix learn_position_controller
```

确认两个路径都来自预期的学习工作区。若指向旧工作区，先解决 source 顺序，再排查 C++ 逻辑。

## 示例 2：按顺序收集运行证据

```bash
ros2 node list
ros2 control list_hardware_components
ros2 control list_hardware_interfaces
ros2 control list_controllers
ros2 topic info /joint_states -v
ros2 topic echo /joint_states --once
```

### 怎样解释这些证据

节点存在只表示进程或节点已出现；硬件 active 表示状态机通过；接口 claimed 表示命令资源已被借出；控制器 active 表示允许周期执行；反馈变化才说明数据链路产生了可观察结果。真实设备还要核对实际运动。

## 排错表

| 现象 | 优先检查 | 修复后怎样验证 |
|---|---|---|
| 找不到包 | 构建结果、source 和安装路径 | ros2 pkg prefix |
| 找不到插件 | 导出宏、XML、CMake 注册、库依赖 | 管理器成功加载硬件 |
| spawner 一直等待 | 管理器是否已收到有效模型 | list_controllers 服务可用 |
| 控制器配置失败 | 参数层级、关节名、接口组合 | inactive 状态 |
| 激活报资源冲突 | 已 claimed 的命令接口 | 原子切换后只剩一个写入者 |
| 发命令无反应 | Topic、类型、长度、时间戳、active 状态 | 目标与反馈一起观察 |
| RViz 不动 | JointState、TF、Fixed Frame、QoS | TF 与模型一致 |
| Gazebo 生成失败 | 惯量、模型转换、插件文件名 | 模型实际存在且管理器启动 |
| 仿真时间不走 | world 是否暂停、/clock 桥 | /clock 连续增加 |
| 轮子动但车不走 | 接触、摩擦、轴向、离地 | 世界位姿与里程计对照 |
| 串口状态过期 | 数据帧、线程错误、下位机是否运行 | 新有效反馈恢复且显式重启 |

## 示例 3：保存一次实验记录

记录以下内容：使用哪个模型与源码版本，当前参数，发送的完整目标，控制器与硬件状态，反馈采样，是否出现错误，以及停止后的状态。

对照总览中的学习验收表，记录当前实验的实际结果。示例输出用于帮助理解；实验记录应使用自己运行得到的状态、反馈和日志。

## 学完后应当能够做到

解释命令如何进入硬件接口；从头创建并运行硬件插件与控制器；区分 RViz 显示、程序模拟、物理仿真和实物；沿源码定位接口与生命周期问题；为具体设备设计反馈、超时与停机流程。

真实硬件接入的最后一步取决于实际设备协议与验证。仿真和虚拟串口通过，不应替代这一部分记录。
