## Behavior Tree 的基本结构与 tick 传播

> 对应 BehaviorTree.CPP 3.8 官方文档：[Learn the Basic Concepts → Introduction to BTs → Basic Concepts](https://www.behaviortree.dev/docs/3.8/learn-the-basics/BT_basics/)。

在前面的学习中，我们已经建立了一个初步对应关系：

```cpp
fsm.update();
```

和 Behavior Tree 中的：

```cpp
tree.tick();
```

都可以理解为：

> 周期性地让决策系统继续向前执行。

但是 Behavior Tree 与普通 FSM 的一个重要区别是：

**一次 `tick()` 会从树的上层节点开始，根据树的结构向下传播。**

---

## Behavior Tree 是一棵由节点组成的树

Behavior Tree，简称 BT，本质上是一棵由若干 `TreeNode` 组成的树。

例如一个非常简单的移动机器人任务：

```text
Mission
└── CheckPathClear
```

其中：

```text
Mission
```

是父节点。

```text
CheckPathClear
```

是它的子节点。

由于 `CheckPathClear` 已经没有子节点，因此它属于：

```text
Leaf Node
```

也就是**叶子节点**。

如果任务继续增加：

```text
Mission
├── CheckBattery
├── Navigate
└── StopRobot
```

那么：

```text
Mission
```

负责组织整个任务。

而：

```text
CheckBattery
Navigate
StopRobot
```

则是它下面的子任务。

Behavior Tree 因此天然具有一种层次化结构：

```text
任务
├── 子任务
│   ├── 更小的任务
│   └── 更小的任务
└── 子任务
```

这也是 Behavior Tree 相比复杂 FSM 的一个重要特点。

FSM 中，任务通常围绕：

```text
状态
状态转换
状态转换条件
```

组织。

Behavior Tree 更强调：

```text
父任务
    ↓
子任务
    ↓
更具体的行为
```

---

## tick 是节点执行的基本驱动方式

在 BehaviorTree.CPP 中，`tick` 是最核心的概念之一。

可以暂时把：

```cpp
node.tick();
```

理解为：

> 让这个节点在当前时刻执行一次自己的逻辑。

官方文档中经常会出现：

```text
tick a node
```

或者：

```text
Node A ticks Node B
```

这里并不是一种特殊通信机制。

它表达的是：

> A 节点决定让 B 节点执行一次。

因此，如果存在：

```text
Mission
└── CheckPathClear
```

一次 Behavior Tree 的执行入口通常可以理解成：

```cpp
root.tick();
```

也就是首先 tick 最上层节点。

---

## tick 从树的上方向下传播

假设行为树是：

```text
        Mission
           |
           ↓
    CheckPathClear
```

当外部开始一次执行：

```cpp
Mission.tick();
```

首先执行的是：

```text
Mission
```

随后，`Mission` 根据自己的规则决定是否继续执行：

```text
CheckPathClear
```

于是形成：

```text
外部
 ↓ tick
Mission
 ↓ tick
CheckPathClear
```

因此，Behavior Tree 中 tick 的基本传播方向是：

```text
Root
 ↓
Parent
 ↓
Child
 ↓
Leaf
```

也就是：

> **tick 从父节点向子节点传播。**

不过这里有一个非常重要的限制：

**父节点决定 tick 是否继续向下传播。**

并不是执行一次：

```cpp
root.tick();
```

就一定会把整棵树所有节点全部执行一遍。

---

## 父节点决定如何 tick 子节点

仍然考虑：

```text
Mission
└── CheckPathClear
```

它的执行逻辑可以暂时用 C++ 风格伪代码理解：

```cpp
NodeStatus Mission::tick()
{
    // 父节点决定让哪个子节点执行
    NodeStatus child_status = CheckPathClear.tick();

    // 根据子节点的执行结果决定自己的结果
    return child_status;
}
```

这里暂时不用关心 BehaviorTree.CPP 的真实 API。

现在只需要理解执行关系：

```text
Mission
   ↓
主动 tick
   ↓
CheckPathClear
```

子节点并不是因为它“挂在树上”就自动执行。

而是因为：

> **父节点主动把 tick 传播给了它。**

以后学习不同 Control Node 时，会看到完全不同的传播规则。

例如某种节点可能按照：

```text
A
完成后
↓
B
完成后
↓
C
```

执行。

另一种节点则可能在：

```text
A 失败
```

之后才尝试：

```text
B
```

这些规则之后再分别学习。

当前只需要记住：

> 父节点负责控制 tick 的传播。

---

## 叶子节点通常执行真正的行为

tick 沿着树不断向下传播，最终通常会到达没有子节点的节点（叶子节点）。

例如：

```text
Mission
└── CheckPathClear
```

其中：

```text
CheckPathClear
```

就是叶子节点。

它可能真正检查移动机器人前方是否可以通行：

```cpp
NodeStatus CheckPathClear::tick()
{
    // 检查前方是否可以继续通行
    if (path_is_clear)
    {
        return NodeStatus::SUCCESS;
    }

    return NodeStatus::FAILURE;
}
```

在之后接入 ROS 2 后，叶子节点还可能执行更加实际的机器人行为。

例如：

```text
NavigateToGoal
      ↓
发送 ROS 2 Action Goal
      ↓
导航系统开始执行任务
```

因此可以先建立一个直觉：

```text
上层节点
    ↓
负责组织任务

叶子节点
    ↓
执行具体行为
```

这不是绝对规则，但对于理解机器人 Behavior Tree 非常有帮助。

---

## 节点执行后会返回状态

节点被 tick 后，会返回自己的执行状态。

BehaviorTree.CPP 中最重要的三个状态是：

```cpp
NodeStatus::SUCCESS
NodeStatus::FAILURE
NodeStatus::RUNNING
```

目前只需要知道它们的大致含义。

```text
SUCCESS
```

表示：

> 当前行为成功完成。

```text
FAILURE
```

表示：

> 当前行为执行失败。

```text
RUNNING
```

表示：

> 当前行为还没有结束，之后还需要继续执行。

因此父节点执行子节点时，可以想象为：

```cpp
NodeStatus child_status = child.tick();
```

父节点拿到这个状态以后，再决定接下来应该如何执行。

---

## tick 向下传播，状态向上返回

假设：

```text
Mission
└── CheckPathClear
```

并且：

```cpp
CheckPathClear.tick();
```

最终返回：

```cpp
NodeStatus::SUCCESS
```

一次完整执行过程可以表示为：

```text
外部
 ↓ tick

Mission
 ↓ tick

CheckPathClear
```

`CheckPathClear` 完成自己的逻辑之后：

```text
CheckPathClear
 ↑ SUCCESS

Mission
```

于是整个过程存在两个方向。

tick 向下：

```text
Parent
   ↓ tick
Child
```

执行状态向上：

```text
Parent
   ↑ status
Child
```

组合起来就是：

```text
          tick
           ↓
        Mission
           ↓
   CheckPathClear
           ↑
        SUCCESS
           ↑
        Mission
```

这就是 Behavior Tree 最核心的执行模型之一：

> **tick 从父节点向子节点传播，执行状态从子节点向父节点返回。**

---

## root.tick() 不等于遍历整棵树

考虑下面的树：

```text
Root
├── A
├── B
└── C
```

执行：

```cpp
root.tick();
```

并不意味着一定会发生：

```text
A
B
C
```

实际执行情况可能是：

```text
A
```

也可能是：

```text
A
↓
B
```

还可能是：

```text
A
↓
B
↓
C
```

具体哪些节点会被执行，取决于：

```text
父节点的类型
+
子节点返回的状态
```

因此更准确的理解不是：

```text
root.tick()
=
执行整棵树
```

而是：

```text
root.tick()
=
从根节点开始一次 Behavior Tree 决策过程
```

然后每一个父节点继续决定：

```text
tick 应该传播给谁
```

## 和 FSM 的 update() 对比

FSM 中可能存在：

```cpp
while (running)
{
    fsm.update();
}
```

其中：

```cpp
fsm.update();
```

负责检查当前状态并推进任务。

Behavior Tree 中以后则可能看到：

```cpp
while (running)
{
    tree.tick();
}
```

但内部组织方式不同。

FSM 更接近：

```cpp
void update()
{
    switch (current_state)
    {
        case State::CHECK:
            break;

        case State::MOVE:
            break;

        case State::STOP:
            break;
    }
}
```

而 Behavior Tree 更接近：

```text
root.tick()
    ↓
Parent
    ↓
Child
    ↓
Leaf
```

也就是说：

```text
FSM
update()
   ↓
根据当前状态执行逻辑
```

而：

```text
Behavior Tree
root.tick()
   ↓
沿树结构传播
   ↓
执行当前需要执行的节点
```

所以：

```text
FSM update() ≈ BT tick()
```

只是一种帮助入门的类比。

两者真正的任务组织方式并不相同。

---

## 本节结论

Behavior Tree 可以看作一棵由节点组成的层次化任务树。

每一次执行都从根节点开始：

```text
Root
 ↓
Parent
 ↓
Child
 ↓
Leaf
```

父节点决定：

```text
是否 tick 子节点
tick 哪个子节点
什么时候 tick 子节点
```

而子节点执行以后，会向父节点返回状态：

```cpp
SUCCESS
FAILURE
RUNNING
```

因此整个执行模型可以浓缩成：

```text
             tick
              ↓
           Parent
              ↓
            Child
              ↓
             Leaf

             Leaf
              ↑
           status
              ↑
           Parent
```

最重要的一句话是：

> **tick 向下传播，状态向上返回，父节点控制 tick 的传播。**

下一部分将在这个基础上继续学习 Behavior Tree 中最重要的三个执行状态：

```cpp
SUCCESS
FAILURE
RUNNING
```

其中 `RUNNING` 将直接关系到机器人导航、机械运动以及 ROS 2 Action 这类持续一段时间才能完成的任务。
