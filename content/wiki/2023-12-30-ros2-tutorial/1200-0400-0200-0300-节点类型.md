## Behavior Tree 的四类基本节点

> 对应 BehaviorTree.CPP 3.8 官方文档：[Learn the Basic Concepts → Introduction to BTs → Types of nodes](https://www.behaviortree.dev/docs/3.8/learn-the-basics/BT_basics/)。

前两节已经介绍了节点之间的执行关系：

```text
父节点
   ↓ tick
子节点
   ↑ SUCCESS / FAILURE / RUNNING
父节点
```

接下来需要知道：**不同类型的节点，在这个过程中分别负责什么。**

BehaviorTree.CPP 将这里要学习的节点分成四类：

| 节点类型 | 中文含义 | 直接子节点数量 | 主要作用 |
| --- | --- | --- | --- |
| `ControlNode` | 控制节点 | 1 到 N 个 | 组织子节点，决定 tick 如何在它们之间传播 |
| `DecoratorNode` | 装饰节点 | 恰好 1 个 | 调整子节点的执行方式，或者处理其返回结果 |
| `ConditionNode` | 条件节点 | 0 个 | 检查条件是否成立 |
| `ActionNode` | 动作节点 | 0 个 | 执行具体操作 |

![](https://cdn.tungchiahui.cn/tungwebsite/assets/images/2023/12/30/1792222597917-0c6d7eea.webp)

这里的数量指的是**直接挂在当前节点下面的子节点**，不是下面整棵子树的节点总数。

例如：

```text
Mission                   [ControlNode]
├── CheckBattery          [ConditionNode]
├── Inverter              [DecoratorNode]
│   └── IsPathBlocked     [ConditionNode]
└── NavigateToGoal        [ActionNode]
```

`Mission` 有三个直接子节点；`Inverter` 有一个；`IsPathBlocked` 没有子节点。

这个示意图只表示节点的分类和包含关系。`Mission` 是任务节点的示例名称，具体采用什么控制规则，要由它实际使用的控制节点类型决定。

## ControlNode：组织子节点的执行

控制节点可以有 **1 到 N 个直接子节点**。

它主要解决的是：

```text
当前应该 tick 哪个子节点？
拿到子节点的结果以后，接下来做什么？
整个控制节点应该返回什么状态？
```

例如移动机器人有三个任务节点：

```text
Mission                   [ControlNode]
├── CheckBattery          [ConditionNode]
├── NavigateToGoal        [ActionNode]
└── StopRobot             [ActionNode]
```

`Mission` 负责组织它们。检查电量、发送导航任务、停止机器人这些具体工作，由下面的叶子节点完成。

控制节点收到父节点传来的 tick 后，会根据自己的规则、当前状态以及子节点返回的状态，决定如何继续传播 tick：

```text
外部或更上层节点
        ↓ tick
     Mission
        ↓ 按控制规则选择子节点
   某个子节点
        ↑ 返回状态
     Mission
        ↑ 按控制规则返回自己的状态
外部或更上层节点
```

因此，控制节点也会返回 `SUCCESS`、`FAILURE` 或 `RUNNING`。它需要把所组织的这部分任务的执行情况报告给上层。

**子节点的结果会影响父节点的结果，但父节点不一定原样返回子节点的状态。** 具体如何处理，取决于控制节点的类型。

### 子节点是有顺序的

官方文档说明，控制节点的子节点是有顺序的。在横向排列的图中通常从左到右表示；本教程的竖向树结构用从上到下表示：

```text
Mission
├── CheckBattery          ← 第一个子节点
├── NavigateToGoal        ← 第二个子节点
└── StopRobot             ← 第三个子节点
```

这个顺序是控制规则的输入之一，但仅凭排列顺序，还不能认定每次 tick 都会执行全部子节点。

后面会学习的：

```text
Sequence
Fallback
```

都属于 `ControlNode`。本节先认识它们的分类，具体执行规则以后单独学习。

`1 到 N 个` 是这一大类的数量范围；某些具体控制节点还会对数量作进一步限制，并不是每一种控制节点都能接受任意数量的子节点。

### 控制节点可以继续包含控制节点

```text
Mission                   [ControlNode]
├── NavigateTask          [ControlNode]
│   ├── CheckPathClear    [ConditionNode]
│   └── NavigateToGoal    [ActionNode]
└── StopRobot             [ActionNode]
```

这样就能把一个大任务拆成更小的任务。上层组织子任务，下层继续组织更具体的节点。

## DecoratorNode：给一个子节点增加执行规则

装饰节点必须有 **恰好一个直接子节点**。

它的基本结构是：

```text
Parent
└── Decorator
    └── Child
```

父节点 tick 装饰节点，装饰节点再按自己的规则决定如何处理 `Child`。

按照 [3.8 官方装饰节点文档](https://www.behaviortree.dev/docs/3.8/nodes-library/DecoratorNode/)，装饰节点可以决定是否 tick 子节点、何时 tick，以及 tick 多少次。它也可以转换子节点的返回结果，或者中止子节点的执行。

例如：

```text
对子节点的成功或失败结果取反
在规定次数内重复执行子节点
对子节点设置执行时间限制
```

这些是不同装饰节点可能提供的能力，不是每个装饰节点同时具有全部能力。

### 用 Inverter 理解结果转换

假设有一个条件节点：

```text
IsPathBlocked
```

它检查前方路径是否被堵住：

```text
有障碍物 → SUCCESS
没有障碍物 → FAILURE
```

在它外面加一个 `Inverter`：

```text
Inverter                  [DecoratorNode]
└── IsPathBlocked         [ConditionNode]
```

就可以把这部分树表达的判断变成：

```text
路径没有被堵住吗？
```

`Inverter` 的状态转换规则是：

| 子节点返回 | Inverter 返回 |
| --- | --- |
| `SUCCESS` | `FAILURE` |
| `FAILURE` | `SUCCESS` |
| `RUNNING` | `RUNNING` |

用 C++ 风格伪代码表示：

```cpp
BT::NodeStatus Inverter::tick()
{
    // 调用唯一子节点的执行入口
    BT::NodeStatus child_status = child.executeTick();

    if (child_status == BT::NodeStatus::SUCCESS)
    {
        return BT::NodeStatus::FAILURE;
    }

    if (child_status == BT::NodeStatus::FAILURE)
    {
        return BT::NodeStatus::SUCCESS;
    }

    // 子节点尚未完成时，取反节点也尚未完成
    return BT::NodeStatus::RUNNING;
}
```

这段代码只展示状态转换，省略了库内部的状态维护。实际调用通常经过框架的 `executeTick()` 入口，再进入节点自己的 `tick()` 等回调；前两节的 `child.tick()` 是对这一过程的概念简写。

上面的 `IsPathBlocked` 是条件节点，本身不会返回 `RUNNING`。表格保留这一行，是因为 `Inverter` 也可以装饰支持 `RUNNING` 的其他节点。

### 一个直接子节点也可以是一整棵子树

```text
Timeout                   [DecoratorNode]
└── NavigateTask          [ControlNode]
    ├── CheckPathClear    [ConditionNode]
    └── NavigateToGoal    [ActionNode]
```

`Timeout` 只有一个直接子节点 `NavigateTask`，因此符合装饰节点的结构要求。

它下面虽然还有多个后代节点，但不影响这个数量限制。装饰节点可以包住叶子节点，也可以包住控制节点或另一个装饰节点。

## ConditionNode：检查条件，不执行改变系统的动作

条件节点没有子节点，属于**叶子节点**。

它通常读取机器人已有的数据，判断某件事是否成立。例如：

```text
CheckBattery      电量是否足够
IsPathClear       路径是否畅通
IsGoalReached     是否已经到达目标
```

结合上一节的状态，条件节点应该返回：

```text
条件成立   → SUCCESS
条件不成立 → FAILURE
```

**BehaviorTree.CPP 3.8 官方要求 ConditionNode 不应改变系统，也不能返回 RUNNING。**

### 电量检查的例子

下面是条件节点执行逻辑的 C++ 风格伪代码。`battery_level` 表示已经获得的电量数据：

```cpp
BT::NodeStatus CheckBattery::tick()
{
    // 读取已有电量数据，只检查，不启动充电或导航
    const double minimum_battery_level = 20.0;

    if (battery_level >= minimum_battery_level)
    {
        return BT::NodeStatus::SUCCESS;
    }

    return BT::NodeStatus::FAILURE;
}
```

电量不足时返回 `FAILURE`，只表示“电量足够”这个条件不成立。它不会自己让机器人去充电，也不表示整个行为树一定失败；上层如何处理，要看父节点的规则。

如果需要让机器人前往充电位置，应另写一个动作节点，例如：

```text
GoToChargingStation       [ActionNode]
```

### 条件节点只有被 tick 时才会检查

```text
父节点
   ↓ tick
CheckBattery
   ↓ 读取当前数据并判断
SUCCESS / FAILURE
   ↑ 返回父节点
```

把 `CheckBattery` 放进树里，并不等于它会持续在后台监控电量。

下一轮是否再次检查，取决于父节点有没有再次 tick 它。因此，某个动作正在执行，也不意味着旁边的条件节点就一定会被反复检查。

条件节点应快速完成当前判断。如果需求是“等待直到电量足够”，其中包含等待过程，就应使用能表达持续执行的动作或树结构，而不是让 ConditionNode 返回 `RUNNING`。

## ActionNode：执行具体操作

动作节点同样没有子节点，也是**叶子节点**。

它负责真正执行操作，例如：

```text
NavigateToGoal      请求导航系统前往目标
StopRobot          请求机器人停止
StartCharging      请求开始充电
```

叶子节点没有行为树子节点，不代表它内部不能调用其他函数或服务。例如 `NavigateToGoal` 可以向外部导航系统发送请求，再读取执行结果。

动作节点的三个状态分别表示：

| 状态 | 对 ActionNode 的含义 |
| --- | --- |
| `SUCCESS` | 动作成功完成 |
| `FAILURE` | 动作失败结束 |
| `RUNNING` | 动作仍在执行，还没有最终结果 |

**检查是否到达目标**和**让机器人前往目标**，因此属于不同职责：

| 节点 | 类型 | 职责 |
| --- | --- | --- |
| `IsGoalReached` | `ConditionNode` | 判断：现在到达了吗？ |
| `NavigateToGoal` | `ActionNode` | 执行：让机器人前往目标 |

### 同步动作：一次调用内得到最终结果

同步动作在当前调用中完成，返回 `SUCCESS` 或 `FAILURE`。

例如一个立即设置指示灯的动作，可以用 C++ 风格伪代码表示：

```cpp
BT::NodeStatus SetStatusLight::tick()
{
    // 假设这是一个能快速完成的本地接口
    const bool command_applied = SetIndicatorLight();

    return command_applied
        ? BT::NodeStatus::SUCCESS
        : BT::NodeStatus::FAILURE;
}
```

在 BehaviorTree.CPP 3.8 中，`SyncActionNode` 明确禁止返回 `RUNNING`；如果返回，框架会抛出异常。

同步调用返回之前，当前树的执行会等待这个调用。因此，适合放在这里的是能快速完成的操作；耗时导航不适合一直堵在同步动作中等待。

### 异步动作：用 RUNNING 表示尚未完成

对于导航这样的持续任务，可以先启动操作，然后快速返回 `RUNNING`，在后续 tick 中继续检查结果：

```text
第一次 tick 到 NavigateToGoal
    ↓
发送一次导航请求
    ↓
RUNNING

后续 tick 再次到达 NavigateToGoal
    ↓
检查已有导航任务的结果
    ├── 尚未结束 → RUNNING
    ├── 成功到达 → SUCCESS
    └── 导航失败 → FAILURE
```

这里每次 tick 都在推进或检查**同一次导航任务**，不是每次重新发送一个导航目标。

当父节点继续选择这个动作时，tick 才会再次到达它。`RUNNING` 本身不会安排下一次 tick，也不会自动创建后台线程；实际工作如何继续，由动作实现及其调用的外部系统决定。

如果上层决定切换任务并中止这个动作，实现中还需要处理取消导航等清理工作。具体中止接口将在异步动作章节学习。

### ActionNode 是分类名称

本节表格中的 `ActionNode` 表示“动作节点”这一类。编写 BehaviorTree.CPP 3.8 的 C++ 节点时，常见的类名是：

```text
ActionNodeBase          动作节点的共同基类
├── SyncActionNode      同步动作
└── StatefulActionNode  用启动、运行、中止回调组织持续任务
```

这只列出了后续常用的类，并不是完整继承树。现在先区分同步和异步的状态约束，具体继承、注册和回调实现留到后面的教程。

相关接口可对照官方 [3.8.0 action_node.h](https://github.com/BehaviorTree/BehaviorTree.CPP/blob/3.8.0/include/behaviortree_cpp_v3/action_node.h)。

## 在一棵树中识别四类节点

回到开头的例子：

```text
Mission                   [ControlNode]
├── CheckBattery          [ConditionNode]
├── Inverter              [DecoratorNode]
│   └── IsPathBlocked     [ConditionNode]
└── NavigateToGoal        [ActionNode]
```

假设某次执行中，`Mission` 的控制规则决定 tick `Inverter`，而此时路径没有被堵住：

```text
Mission
   ↓ tick
Inverter
   ↓ tick
IsPathBlocked
   ↑ FAILURE：路径没有被堵住
Inverter
   ↑ SUCCESS：对检查结果取反
Mission
```

`Mission` 收到结果后，继续按自己的控制规则决策。这个例子没有规定它接下来一定 tick 哪个子节点。

从位置上看，ControlNode 和 DecoratorNode 都有子节点，负责组织或包装下面的节点；ConditionNode 和 ActionNode 没有子节点，tick 到这里就不再向行为树子节点传播，而是执行检查或操作，再向上返回状态。

不过，**节点类型不等于固定的树层级**。控制节点可以嵌套，装饰节点可以位于根部，也可以夹在其他节点之间；一棵只有一个动作节点的树，也可以直接以这个动作为根节点。

`Root`、`Parent`、`Child`、`Leaf` 描述节点在树中的位置或关系；本节的四类节点描述职责和结构约束。以后阅读一棵树时，可以先看每个节点有几个子节点，再看它如何传播 tick、如何处理状态。

下一节将开始学习具体控制节点的执行规则。
