## 行为树（Behavior Tree.CPP）

> 对应 BehaviorTree.CPP 3.8 官方文档：[About](https://www.behaviortree.dev/docs/3.8/intro)。

### 官方教程

[官方教程BT.CPP v3.8](https://www.behaviortree.dev/docs/3.8)

### 从 FSM 走向 Behavior Tree

我们先不碰 BehaviorTree.CPP API、不写 XML，也不创建工程。

这一阶段只解决一个问题：

> 既然有限状态机已经能控制机器人任务，为什么还要引入 Behavior Tree？

这正是 BehaviorTree.CPP 3.8 官方 [About](https://www.behaviortree.dev/docs/3.8/intro) 页首先想建立的认识。
官方对 BT 的定义是：Behavior Tree 用来组织自主体（例如机器人）不同任务之间的切换；并强调它的主要特点是模块化、层次化和反应性。

#### 先回忆你已经会的 FSM

假设小车只有三个任务：

```text
等待
 ↓
导航
 ↓
到达目标
```

用你已经学过的状态机，大概会是：

```cpp
enum class RobotState
{
    IDLE,
    NAVIGATING,
    ARRIVED
};

RobotState current_state = RobotState::IDLE;

void update()
{
    switch (current_state)
    {
        case RobotState::IDLE:
        {
            if (hasNavigationGoal())
            {
                startNavigation();
                current_state = RobotState::NAVIGATING;
            }
            break;
        }

        case RobotState::NAVIGATING:
        {
            if (navigationSucceeded())
            {
                current_state = RobotState::ARRIVED;
            }
            else if (navigationFailed())
            {
                current_state = RobotState::IDLE;
            }

            // 没成功也没失败：
            // 保持 NAVIGATING，下一周期继续检查
            break;
        }

        case RobotState::ARRIVED:
        {
            stopRobot();
            break;
        }
    }
}
```

这个东西其实完全没问题。

而且你之前学过的：

```cpp
while (running)
{
    update();

    // 周期执行，而不是在某个状态里面 sleep 等待
}
```

这个思想非常重要，因为将来学 Behavior Tree 时，你会发现它和 BT 的周期 tick 有很强的对应关系。

#### FSM 真正麻烦的地方不是“三个状态”

三个状态当然很好写。

问题通常出现在机器人任务越来越复杂之后。

假设最开始只有：

```text
IDLE
  ↓
NAVIGATING
  ↓
ARRIVED
```

后来增加导航失败：

```text
IDLE
  ↓
NAVIGATING ──失败──→ IDLE
  ↓成功
ARRIVED
```

依然很好处理。

但是继续增加：

```text
低电量
紧急停止
定位丢失
传感器异常
导航失败
导航重试
收到新的导航目标
任务取消
```

情况就开始变化了。

例如加入低电量处理以后：

```cpp
case RobotState::IDLE:
{
    if (batteryLow())
    {
        current_state = RobotState::CHARGING;
        break;
    }

    // 处理 IDLE 自己的逻辑
    break;
}

case RobotState::NAVIGATING:
{
    if (batteryLow())
    {
        cancelNavigation();
        current_state = RobotState::CHARGING;
        break;
    }

    // 处理 NAVIGATING 自己的逻辑
    break;
}

case RobotState::ARRIVED:
{
    if (batteryLow())
    {
        current_state = RobotState::CHARGING;
        break;
    }

    // 处理 ARRIVED 自己的逻辑
    break;
}
```

同一个：

```cpp
batteryLow()
```

已经开始影响多个状态。

如果再加入全局紧急停止：

```cpp
if (emergencyStopRequested())
```

那么等待、导航、充电、执行任务等很多状态都可能需要处理它。

因此，FSM 复杂以后真正麻烦的往往不仅是：

```text
状态数量增加
```

而是：

```text
状态之间的转换关系增加
```

一个状态已经无法单独理解。

例如看到：

```cpp
RobotState::NAVIGATING
```

还必须知道：

```text
谁能进入 NAVIGATING？

NAVIGATING 可以退出到哪里？

低电量怎么办？

紧急停止怎么办？

定位失败怎么办？

导航失败怎么办？

收到新目标怎么办？
```

随着系统继续扩大，状态之间的耦合会越来越明显。

#### 跨状态需求

机器人中还有很多需求并不真正属于某个状态。

例如：

```cpp
emergencyStopRequested()
```

紧急停止属于整个机器人的安全需求。

它可能应该比：

```text
等待
导航
充电
执行任务
```

都有更高优先级。

如果直接使用比较简单的 FSM 写法，很容易出现：

```text
IDLE:
    检查急停

NAVIGATING:
    检查急停

CHARGING:
    检查急停

DOING_TASK:
    检查急停
```

于是原本属于整个机器人的任务逻辑，被逐渐分散到不同状态中。

BehaviorTree.CPP 官方教程强调，一个良好的软件架构应该具有：

```text
Modularity             模块化
Reusability            可复用性
Composability          可组合性
Separation of Concerns 关注点分离
```

对于机器人，可以把系统大致理解成：

```text
底层能力
│
├── Navigation
├── Localization
├── Battery
├── Sensors
└── Actuator

        ↑

任务编排 / 决策逻辑
```

例如导航模块主要解决：

```text
“给我一个目标，如何导航过去？”
```

而更上层的任务逻辑决定：

```text
“现在是否应该导航？”

“应该导航到哪里？”

“导航失败以后怎么办？”

“低电量时是否应该暂时放弃当前任务？”
```

Behavior Tree 很适合用于组织这一层任务逻辑。

官方对 Behavior Tree 的定义就是：

> Behavior Tree 是一种用于组织自主体（例如机器人）不同任务之间切换的结构。

#### Behavior Tree 换了一种思考方式

FSM 很自然的思考方式是：

```text
我现在处于什么状态？
        ↓
发生了什么事件？
        ↓
应该转移到哪个状态？
```

例如：

```cpp
if (current_state == RobotState::NAVIGATING)
{
    if (batteryLow())
    {
        current_state = RobotState::CHARGING;
    }
}
```

而 Behavior Tree 更倾向于描述：

```text
机器人现在应该优先做什么？
```

例如暂时用概念结构表示：

```text
Robot Behavior
│
├── 如果发生紧急情况
│      └── 停止机器人
│
├── 如果电量低
│      └── 处理充电
│
├── 如果存在导航目标
│      └── 执行导航
│
└── 否则
       └── 等待
```

这里还不是正式的 Behavior Tree。

暂时不需要考虑：

```text
Sequence
Fallback
Condition
Action

SUCCESS
FAILURE
RUNNING
```

现在只需要观察思想上的区别。

FSM 更像是在描述：

```text
NAVIGATING 怎样转移到 CHARGING？
```

Behavior Tree 更倾向于描述：

```text
紧急情况优先级最高。

否则：
    电量低就处理电量问题。

否则：
    有导航任务就执行导航。

否则：
    等待。
```

机器人行为逐渐从：

```text
状态之间的一堆连线
```

变成：

```text
具有层次关系的任务结构
```

#### Hierarchical：层次化

Behavior Tree 的一个重要特点是：

```text
Hierarchical
```

也就是层次化。

复杂行为可以由多个较小行为组成，一个完整的子树又可以继续作为更大行为的一部分。

例如：

```text
Robot
│
├── Safety
│
│   ├── EmergencyStop
│   └── SensorCheck
│
├── EnergyManagement
│
│   ├── CheckBattery
│
│   └── Recharge
│
└── ExecuteMission
    │
    ├── CheckGoal
    │
    └── Navigate
        │
        ├── PlanPath
        ├── FollowPath
        └── CheckArrival
```

如果只关心机器人的整体行为，可以看：

```text
Robot
├── Safety
├── EnergyManagement
└── ExecuteMission
```

如果只研究导航，可以继续展开：

```text
Navigate
├── PlanPath
├── FollowPath
└── CheckArrival
```

这就是行为树的层次结构。

#### Modularity：模块化

BehaviorTree.CPP 官方把 Tree Node 比喻成可以组合起来的 building blocks，也就是积木。

例如以后可能存在：

```text
IsBatteryLow
HasNavigationGoal
NavigateToGoal
StopRobot
IsLocalizationValid
```

每个节点只负责相对独立的问题。

例如：

```cpp
bool isBatteryLow()
{
    // 只负责判断当前电量是否过低
}
```

而不是让一个函数同时负责：

```text
检测电量
停止导航
决定任务
开始返航
修改机器人状态
处理定位
……
```

这种相对独立的节点更加容易：

```text
复用
测试
组合
替换
```

#### Composability：可组合性

Behavior Tree 不仅要求功能被拆分，还强调这些功能能够重新组合。

例如：

```text
CheckGoal
    +
Navigate
    +
CheckArrival
    ↓
NavigationTask
```

进一步：

```text
NavigationTask
    +
RechargeTask
    +
SafetyTask
    ↓
RobotBehavior
```

于是小的行为可以组成更大的行为，更大的行为又可以继续作为其他行为的一部分。

#### Reactive：反应性

机器人工作的现实环境一直在变化。

例如：

```text
t = 0 s

电量正常
定位正常
存在导航目标

→ 开始导航
```

运行一段时间后：

```text
t = 5 s

EmergencyStop = true
```

机器人应该能够及时对新的情况作出反应，而不是必须等当前任务完全执行结束之后才重新检查环境。

这就是 Behavior Tree 中非常重要的：

```text
Reactive
```

也就是反应性。

#### 从 update() 到 tick()

之前的非阻塞 FSM 通常会周期执行：

```cpp
while (running)
{
    update();

    // 周期执行，而不是长时间阻塞在某一个状态中
}
```

每次执行 `update()`，状态机都可以重新检查：

```text
有没有新事件？
任务完成了吗？
任务失败了吗？
外界条件变化了吗？
```

Behavior Tree 同样具有周期执行的思想。

以后会看到一个非常重要的概念：

```text
tick
```

现在可以先建立一个粗略对应：

```text
FSM

while (running)
{
    update();
}
```

以及：

```text
Behavior Tree

while (running)
{
    tick();
}
```

二者在“周期检查”这一思想上比较接近，但内部工作方式不同。

FSM 的 `update()` 往往是：

```text
读取 current_state
        ↓
执行当前 state
        ↓
根据事件决定是否发生状态转移
```

Behavior Tree 的一次 `tick` 更接近：

```text
从行为树顶部开始
        ↓
根据当前条件沿树向下执行
        ↓
决定这一周期需要执行哪些节点
```

后续会正式学习：

```text
tick 是什么？

节点为什么需要返回状态？

SUCCESS、FAILURE、RUNNING 分别代表什么？
```

#### Behavior Tree 并不是 FSM 的替代品

不要简单理解成：

```text
FSM 很落后
Behavior Tree 更高级
```

它们适合解决的问题并不完全相同。

例如一个设备只有：

```text
OFF
STARTING
RUNNING
ERROR
```

使用 FSM 可能非常合适。

甚至 Behavior Tree 中的某个 Action 节点内部，也完全可以继续使用 FSM：

```text
Behavior Tree
│
└── Navigate
       │
       └── Navigation Controller
              │
              └── FSM
```

可以粗略理解成：

```text
FSM

适合：
明确的状态 + 明确的状态转移
```

而：

```text
Behavior Tree

适合：
复杂任务组织
层次化组合
动态条件
反应式行为
```

两者并不是互相排斥的关系。

#### 从 FSM 到 Behavior Tree

这一阶段可以总结成：

```text
简单机器人任务
      ↓
FSM 很容易描述
      ↓
任务越来越复杂
      ↓
状态越来越多
      +
跨状态条件越来越多
      +
状态转移越来越多
      ↓
行为逻辑开始耦合、分散
      ↓
希望把任务组织逻辑集中起来
      ↓
把行为拆成可复用模块
      ↓
使用层次结构组合模块
      ↓
周期重新评估当前应该做什么
      ↓
Behavior Tree
```

到这里暂时不需要学习任何 BehaviorTree.CPP API。

只需要先建立一个认识：

> Behavior Tree 的核心价值并不是把 FSM 的 `state` 换一个名字，而是提供一种模块化、层次化、可组合并具有反应性的方式来组织复杂行为。
