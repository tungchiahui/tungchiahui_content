## C++ 实现节点，XML 组织节点

可以把一个程序分成三部分：

| 部分 | 负责什么 | 例子 |
| --- | --- | --- |
| C++ 节点 | 实现具体检查或操作，声明输入输出接口 | 检查电量、选择目标、打印目标 |
| XML | 描述树的结构，配置节点参数和数据连接 | 把三个节点放进 `Sequence` |
| 外部程序 | 注册节点、创建树、驱动执行 | `BehaviorTreeFactory`、`tickRoot()` |

例如：

```text
C++ 注册可用的节点类型
    ↓
工厂读取 XML，创建具体节点实例并连接成树
    ↓
外部 tick 根节点
    ↓
按树的规则调用各节点的回调
```

“注册节点”是告诉工厂：遇到某个类型标识时，怎样创建对应的 C++ 节点。它不会立即执行任务。

例如 `factory.registerNodeType<PrintGoal>("PrintGoal")` 将字符串 `PrintGoal` 与 C++ 类关联；之后 XML 中每出现一次 `<PrintGoal/>`，工厂就可以创建一个实例。注册类型和创建实例是两个步骤，同一类型可以创建多个实例。

普通自定义节点通常通过继承实现，例如继承 `ConditionNode`、`SyncActionNode`。简单检查也可以通过 `registerSimpleCondition()` 包装函数或 lambda，简单同步动作可以用 `registerSimpleAction()`。

树通常在程序初始化时创建一次，后续反复 tick，而不是每轮重新解析 XML。调整已有节点的排列或配置后，可以重新运行程序加载新的 XML；新增 C++ 节点实现时，仍要重新编译。

## 用 XML 描述一棵完整的树

下面是本篇逐步扩展后的 XML，用来认识文件结构。实践部分会先运行更小的树，最后再得到这个版本：

```xml
<root main_tree_to_execute="MainTree">
    <BehaviorTree ID="MainTree">
        <Sequence name="mission_sequence">
            <CheckBattery name="check_battery"/>
            <SelectGoal name="select_goal" goal="{mission_goal}"/>
            <PrintGoal name="print_goal" goal="{mission_goal}"/>
        </Sequence>
    </BehaviorTree>
</root>
```

它对应：

```text
Sequence
├── CheckBattery
├── SelectGoal      输出选定的目标
└── PrintGoal       读取并打印该目标
```

### 分清 XML 中几种不同的标识

| 写法 | 含义 |
| --- | --- |
| `<root>` | XML 文档的外层容器，不是可执行的行为树节点 |
| `main_tree_to_execute="MainTree"` | 指定默认执行哪棵树 |
| `<BehaviorTree ID="MainTree">` | 定义一棵名叫 `MainTree` 的树 |
| `<Sequence>` | 这棵树实际的根节点 |
| `<PrintGoal>` | 注册到工厂的节点类型标识，必须能找到对应实现 |
| `name="print_goal"` | 当前节点实例的名称，便于日志和调试，可省略 |
| `goal="{mission_goal}"` | 把节点的 `goal` 端口连接到 Blackboard 的 `mission_goal` 条目 |

因此，树的 `ID`、节点类型的注册标识、实例的 `name` 和数据条目的名称，各自有不同用途。

一个 XML 文件可以定义多棵 `<BehaviorTree>`；每棵树下面应有一个实际根节点。
只有一棵树时，可以省略 `main_tree_to_execute`；
有多棵树、需要从文件直接确定默认入口时，应明确填写。

XML 中的父子关系仍遵守前面的结构约束：控制节点包含一个或多个子节点，装饰节点包含一个，条件和动作节点没有子节点。

## Ports 与 Blackboard：让数据在节点之间流动

执行状态和业务数据走的是不同的通道：

```text
SUCCESS / FAILURE / RUNNING   告诉父节点任务的执行情况
Ports + Blackboard           传递目标、路径、观测值等业务数据
```

节点的输入输出端口类似函数接口；
Blackboard 则用键值条目保存数据：

| 概念 | 本例中的作用 |
| --- | --- |
| 输出端口 `OutputPort` | `SelectGoal` 通过 `goal` 端口写出目标 |
| Blackboard 条目 | 使用键 `mission_goal` 保存目标值 |
| 输入端口 `InputPort` | `PrintGoal` 通过自己的 `goal` 端口读取目标 |

连接过程是：

```text
SelectGoal 的输出端口 goal
    ↓ setOutput()
Blackboard["mission_goal"] = "loading_area"
    ↓ getInput()
PrintGoal 的输入端口 goal
```

两个端口恰好都叫 `goal`，但真正把它们连接起来的是 XML 中相同的 `{mission_goal}`。
生产者和消费者的端口名称可以不同，只要它们映射到同一个条目。

### 固定值与 Blackboard 引用

下面两种输入配置含义不同：

```xml
<PrintGoal goal="loading_area"/>
<PrintGoal goal="{mission_goal}"/>
```

第一种直接提供固定字符串；
第二种读取 Blackboard 中键为 `mission_goal` 的值。

花括号表达条目引用，不是 C++ 指针，也不会自动创建有效的业务数据。

读取前必须有人写入该值，例如前面的输出节点，或者由外部程序初始化 Blackboard。引用了一个从未写入的条目，输入读取就会失败。

### 接口由 C++ 声明，连接由 XML 配置

节点用静态方法 `providedPorts()` 声明端口的名称、方向和 C++ 类型。
XML 则给端口配置固定值，或把它映射到 Blackboard。

输入使用 `getInput<T>()`，输出使用 `setOutput()`。
读取可能因为缺少数据、类型或转换问题而失败，节点需要检查结果；本篇选择在配置错误时抛出异常，由主程序报告。

应在执行回调中读取输入，让后续执行能取得当前值。不要只在构造函数中读取一次，再假定这个值永远不变。

Blackboard 可以保存多种 C++ 类型，并不限于字符串；从 XML 文本转换自定义类型、双向端口以及子树的数据映射，会在后面的数据传递实践中学习。

## 认识 XML 中的几种补充写法

### 简写与显式写法

下面两种写法指向同一种动作节点：

```xml
<PrintGoal name="print_goal" goal="loading_area"/>
<Action ID="PrintGoal" name="print_goal" goal="loading_area"/>
```

前者直接把注册标识写作标签名；
后者用 `Action` 指明分类，再用 `ID` 指定注册标识。
本教程以简写为主。

XML 中还可能出现 `<TreeNodeModel>`，为 Groot 等工具提供自定义节点的分类和端口描述。
它是模型信息，不是执行分支，也不会替代 C++ 节点注册。
运行本篇示例时不需要额外填写它。

### 用 SubTree 引用另一棵树

同一个 XML 中可以定义并复用一段行为：

```xml
<root main_tree_to_execute="MainTree">
    <BehaviorTree ID="MainTree">
        <Sequence>
            <CheckBattery/>
            <SubTree ID="ReportTask"/>
        </Sequence>
    </BehaviorTree>

    <BehaviorTree ID="ReportTask">
        <PrintGoal goal="loading_area"/>
    </BehaviorTree>
</root>
```

这里先检查电量，再执行 `ReportTask`。
`<SubTree ID="ReportTask"/>` 引用的是树定义，不是普通 C++ 动作类；工厂在创建树时展开并建立相应结构。

所以这个 XML 标签本身虽然没有嵌套内容，运行时仍连接到所引用的子树。子树如何传数据，需要明确考虑其 Blackboard 范围，后面再讲。

### 用 include 拆分文件

也可以在 `<root>` 中写：

```xml
<include path="report_task.xml"/>
```

它把其他 XML 中的树定义引入当前文件，再通过 `SubTree` 使用。
相对路径以包含它的 XML 文件位置为基准；引入定义不会自动执行一遍那棵树。

另一种方式是在 C++ 中用 `registerBehaviorTreeFromFile()` 加载各个文件的树定义，再用 `createTree("MainTree")` 创建选定的树。
当前先掌握单文件示例，多文件组织留到任务组合时实践。

### 调整工程名称并沿用模板配置

将顶层 `CMakeLists.txt` 里的`project(cmake_template VERSION 1.0.0 LANGUAGES C CXX)`改成`project(bt_first_tree VERSION 1.0.0 LANGUAGES C CXX)`，主要是把项目名改成 `bt_first_tree`。

当前模板已经使用下列配置，保留原值即可：

| 文件与位置 | 当前配置 |
| --- | --- |
| 顶层 `CMakeLists.txt` 的最低版本声明 | `cmake_minimum_required(VERSION 3.22)` |
| `CMakePresets.json` 顶层的 `version` | `3` |
| `CMakePresets.json` 中的 `cmakeMinimumRequired` | `major: 3`、`minor: 22`、`patch: 0` |

其中，预设文件的 `version` 表示 JSON 格式版本，`cmakeMinimumRequired` 表示工程要求的 CMake 版本。
当前预设只使用格式 `3` 已支持的功能，说明见 [CMake 3.22 预设文档](https://cmake.org/cmake/help/v3.22/manual/cmake-presets.7.html#format)。

### 集中保存行为树依赖配置

将以下完整内容保存到新增的 `cmake/BehaviorTree.cmake`。这份配置只准备一次，后续几轮不用反复修改。它先查找已安装的 **3.8.7**；未找到对应版本时，再获取同一版本的源码：

```cmake
include_guard(GLOBAL)

# 优先查找当前构建环境中已安装的目标版本
find_package(behaviortree_cpp_v3 3.8.7 EXACT QUIET CONFIG)

if(behaviortree_cpp_v3_FOUND)
    # ROS 包和独立安装的源码包可能导出不同名称的 CMake target
    if(TARGET behaviortree_cpp_v3::behaviortree_cpp_v3)
        set(BTCPP_TARGET behaviortree_cpp_v3::behaviortree_cpp_v3)
    elseif(TARGET BT::behaviortree_cpp_v3)
        set(BTCPP_TARGET BT::behaviortree_cpp_v3)
    else()
        message(FATAL_ERROR "BehaviorTree.CPP 3.8.7 was found without a supported target")
    endif()
    message(STATUS "Using installed BehaviorTree.CPP 3.8.7: ${behaviortree_cpp_v3_DIR}")
else()
    include(FetchContent)

    # 未安装目标版本时，固定获取 3.8.7 源码
    set(BUILD_EXAMPLES OFF CACHE BOOL "" FORCE)
    set(BUILD_UNIT_TESTS OFF CACHE BOOL "" FORCE)
    set(BUILD_TOOLS OFF CACHE BOOL "" FORCE)
    set(BUILD_MANUAL_SELECTOR OFF CACHE BOOL "" FORCE)
    set(ENABLE_COROUTINES OFF CACHE BOOL "" FORCE)

    FetchContent_Declare(
        behaviortree_cpp_v3
        URL https://codeload.github.com/BehaviorTree/BehaviorTree.CPP/tar.gz/refs/tags/3.8.7
    )
    FetchContent_MakeAvailable(behaviortree_cpp_v3)

    # 3.8.7 会创建 sample_nodes，本篇将它排除在默认构建之外
    set_property(DIRECTORY "${behaviortree_cpp_v3_SOURCE_DIR}/sample_nodes"
        PROPERTY EXCLUDE_FROM_ALL TRUE)

    set(BTCPP_TARGET behaviortree_cpp_v3)
    message(STATUS "Building BehaviorTree.CPP 3.8.7 from source")
endif()
```

在已加载 ROS 2、能找到安装包的 Humble 环境中，Configure 输出会包含 `Using installed BehaviorTree.CPP 3.8.7`，并显示包配置所在路径。此时直接链接容器里的库，不下载或重新编译它。当前构建环境找不到该版本时，则显示 `Building BehaviorTree.CPP 3.8.7 from source`。

复用 Humble 安装包时，配置和运行程序都需要 ROS 2 环境。本篇测试在加载 `/opt/ros/humble/setup.bash` 后完成；VSCode 的 CMake Tools 与运行、调试进程也应继承这份环境。
只在已打开窗口的集成终端中加载环境，不会自动更新扩展进程。
未准备 ROS 2 环境的独立工程可以使用同版本源码分支，程序本身不需要启动 ROS 节点。

`BTCPP_TARGET` 保存本次应链接的 CMake target，主程序统一使用这个变量。这样两种依赖来源使用同一份 C++ 和 XML，框架也不需要手动切换。

源码分支的构建选项可对照官方 [3.8.7 CMakeLists.txt](https://github.com/BehaviorTree/BehaviorTree.CPP/blob/3.8.7/CMakeLists.txt)。3.8.7 不再提供 `BUILD_SAMPLES` 开关，所以本篇直接将 `sample_nodes` 排除在默认构建之外。关闭协程不影响本篇同步节点，也不影响后面使用 `StatefulActionNode`。

3.8.7 的源码分支已在 GCC 16 环境中构建运行通过，配置无需额外添加模板兼容选项。

### 注册简单动作与创建树的 API

`BT::BehaviorTreeFactory factory;` 创建一个节点工厂对象，本例不需要给构造函数传参。
后面的注册操作告诉工厂怎样创建自定义节点；加载 XML 时，工厂再按注册名创建节点实例。

下面的函数声明用于理解接口，不用再次粘贴到工程中。
原型按官方 [3.8.7 bt_factory.h](https://github.com/BehaviorTree/BehaviorTree.CPP/blob/3.8.7/include/behaviortree_cpp_v3/bt_factory.h) 核对。

#### `registerSimpleAction()`

函数原型：

```cpp
void registerSimpleAction(
    const std::string& ID,
    const BT::SimpleActionNode::TickFunctor& tick_functor,
    BT::PortsList ports = {});
```

作用：把一个回调函数注册成简单同步动作，之后可以在 XML 中使用对应的节点名。

| 参数 | 类型与含义 | 本例传入 |
| --- | --- | --- |
| 第一个 `ID` | 字符串，注册到工厂的节点类型名称，对应 XML 标签 | `"ReportReady"`，对应 `<ReportReady/>` |
| 第二个 `tick_functor` | 执行该节点时调用的函数，签名为 `BT::NodeStatus(BT::TreeNode&)` | 普通函数 `ReportReady` |
| 第三个 `ports` | 可选的端口声明，类型为 `BT::PortsList`，默认空列表 | 省略，因为这个最小动作不读写端口 |

第二个参数传的是 **`ReportReady` 函数本身**，没有调用括号。注册时先保存回调；树执行到这个动作时，框架才调用它，并传入代表当前节点实例的 `BT::TreeNode&`。本例不使用这个引用，所以函数定义中只保留类型，没有写形参名。

返回值：`void`，注册函数本身不返回任务状态；`ReportReady()` 回调返回的 `BT::NodeStatus` 才是节点执行结果。这个简单动作属于同步动作，回调应返回 `SUCCESS` 或 `FAILURE`，不能返回 `RUNNING`。注册名重复等注册错误会抛出异常。

#### `createTreeFromFile()`

函数原型：

```cpp
BT::Tree createTreeFromFile(
    const std::string& file_path,
    BT::Blackboard::Ptr blackboard = BT::Blackboard::create());
```

作用：读取 XML 文件，并按照工厂已有的节点类型和 XML 结构创建一棵树。

| 参数 | 含义 | 本例用法 |
| --- | --- | --- |
| 第一个 `file_path` | 入口 XML 的路径字符串 | `BT_XML_PATH`，由 CMake 提供的完整文件路径 |
| 第二个 `blackboard` | 可选，指定根树使用的 Blackboard | 本例省略，由默认参数创建；下一篇会从外部传入 |

返回值：`BT::Tree`，本例用 `auto tree` 接收。创建时会构造节点并检查 XML，但还没有开始执行动作的 `tick()`。文件不存在、XML 错误或使用未注册节点等情况会抛出异常。

#### `tickRoot()` 与 `BT::toStr()`

`tree.tickRoot()` 不接收参数，返回 `BT::NodeStatus`。调用一次，就从根节点驱动一次；一次根 tick 可能继续执行多个立即完成的节点，也可能在某个节点返回 `RUNNING` 时先返回主程序。

`BT::toStr(result)` 的参数是需要显示的节点状态，返回对应的 `std::string`，例如 `SUCCESS`。它只负责把状态变成文本；真正决定程序退出码的仍是后面的状态比较。

## 将打印动作换成带输入端口的节点类

现在希望目标可以从 XML 配置。把原来固定打印“机器人已就绪”的动作，换成读取并打印 `goal` 的 `PrintGoal`。

这一轮只增加输入端口，先使用 XML 固定字符串；下一轮再连接 Blackboard。

### 添加头文件并替换动作实现

保留 `bt_factory.h` 和 `<iostream>`，再在文件顶部增加两个头文件：

```cpp
#include <exception>
#include <string>
```

删除原来的 `ReportReady()` 函数，换成下面的完整 `PrintGoal` 类;
`CheckBattery()` 函数继续保留，电量恢复为 `80.0`：

```cpp
class PrintGoal : public BT::SyncActionNode
{
public:
    PrintGoal(const std::string& name, const BT::NodeConfiguration& config)
        : BT::SyncActionNode(name, config)
    {}

    static BT::PortsList providedPorts()
    {
        // 节点需要一个名为 goal 的字符串输入
        return {BT::InputPort<std::string>("goal")};
    }

    BT::NodeStatus tick() override
    {
        // 每次执行时读取输入，读取成功后再使用
        auto goal = getInput<std::string>("goal");
        if (!goal)
        {
            throw BT::RuntimeError("Cannot read input [goal]: ", goal.error());
        }

        std::cout << "[PrintGoal] target=" << goal.value() << '\n';
        return BT::NodeStatus::SUCCESS;
    }
};
```

类里的几个部分各有职责：

| 部分 | 作用 |
| --- | --- |
| 继承 `BT::SyncActionNode` | 表示这是立即完成的同步动作 |
| 构造函数 | 将实例名称和配置交给基类保存 |
| `providedPorts()` | 声明字符串输入端口 `goal` |
| `tick()` | 读取目标，打印后返回成功 |

#### 构造函数的 `name` 与 `config`

本例构造函数的两个参数由工厂在创建节点实例时提供：

| 参数 | 类型 | 含义 |
| --- | --- | --- |
| 第一个 `name` | `const std::string&` | 当前节点的实例名称；XML 可以用 `name` 属性设置，省略时通常使用节点的注册名 |
| 第二个 `config` | `const BT::NodeConfiguration&` | 当前实例的配置，包含 Blackboard，以及输入、输出端口的映射 |

初始化列表中的 `BT::SyncActionNode(name, config)` 将这两个参数交给基类保存，后面的 `getInput()` 才能按本实例的 XML 配置读取数据。
这里不需要在 `main()` 中手动调用 `PrintGoal` 的构造函数。

#### `providedPorts()` 与 `InputPort<T>()`

`static BT::PortsList providedPorts()` 不接收参数，返回本节点的端口声明。它是自定义节点按约定提供的静态函数，工厂注册节点类时会读取它；声明里保存的是接口信息，实际目标值由 XML 或 Blackboard 提供。

本例使用 `BT::InputPort<std::string>("goal")`：

| 位置 | 含义 |
| --- | --- |
| 模板参数 `<std::string>` | 输入值的 C++ 类型 |
| 第一个函数参数 `"goal"` | 节点自己的输入端口名，对应 XML 的 `goal` 属性 |
| 可选的第二个函数参数 | 端口说明文字，本例省略；带默认值的三参数形式在下一篇说明 |

返回值：一个端口名称和 `BT::PortInfo` 组成的键值对，加入 `BT::PortsList` 后供工厂使用。这次调用声明端口，不会立即读取目标。

#### `getInput<T>()` 的参数与返回值

本例使用的原型为：

```cpp
template <typename T>
BT::Optional<T> getInput(const std::string& key) const;
```

作用：根据当前节点的端口映射读取输入，并按 `T` 获取或转换数据。

- 模板参数 `T` 是期望读取的类型，本例为 `std::string`。
- 唯一的函数参数 `key` 是**节点自己的端口名**，本例为 `"goal"`。XML 决定它来自固定文本还是某个 Blackboard 条目。

返回值：`BT::Optional<T>`，这是 BehaviorTree.CPP 使用的带错误信息的结果类型。先用 `if (!goal)` 判断读取是否失败；有效时用 `goal.value()` 取得值，失败时用 `goal.error()` 取得错误字符串。

`throw BT::RuntimeError("Cannot read input [goal]: ", goal.error());` 将固定提示和库返回的错误信息组成异常，再交给 `main()` 的 `catch` 显示。`BT::RuntimeError` 是库提供的异常类型，可以被 `const std::exception&` 捕获。接口细节见 [3.8.7 tree_node.h](https://github.com/BehaviorTree/BehaviorTree.CPP/blob/3.8.7/include/behaviortree_cpp_v3/tree_node.h)。

#### `registerNodeType<T>()` 的参数

本例使用的原型为：

```cpp
template <typename T>
void registerNodeType(const std::string& ID);
```

作用：将一个自定义节点类注册到工厂，让工厂能够按 XML 创建该类的实例。

| 位置 | 含义 | 本例 |
| --- | --- | --- |
| 模板参数 `T` | C++ 中已经定义的节点类 | `PrintGoal` |
| 第一个函数参数 `ID` | XML 使用的注册名 | `"PrintGoal"`，对应 `<PrintGoal/>` |

`<PrintGoal>` 是模板参数，`("PrintGoal")` 中的字符串才是函数实参。这两个名字在本例中保持一致以便阅读；C++ 类名和 XML 注册名分别负责不同的一层。

返回值：`void`。注册时读取这个类的端口声明并保存创建方式；加载 XML 时，工厂再为每个节点实例提供 `name` 和 `config`，调用前面说明的构造函数。

```cpp
        return result == BT::NodeStatus::SUCCESS ? 0 : 1;
```

固定值已经能读到了，现在让前面的节点产生目标，后面的节点通过 Blackboard 读取。保留上一轮的 `PrintGoal`、`CheckBattery()` 和 `main()`，只增加一个类和一行注册。

### 增加 SelectGoal 类并注册

在 `PrintGoal` 类前面加入：

```cpp
class SelectGoal : public BT::SyncActionNode
{
public:
    SelectGoal(const std::string& name, const BT::NodeConfiguration& config)
        : BT::SyncActionNode(name, config)
```

```cpp

```

工厂已有 `Sequence` 等内置节点；本轮只是多注册一种自定义动作类型，不需要修改构建配置。

#### `OutputPort<T>()` 与 `setOutput()`

`BT::OutputPort<std::string>("goal")` 声明字符串输出端口：模板参数指定值类型，第一个函数参数是端口名，可选的第二个参数是说明文字。返回值同样是用于组成 `BT::PortsList` 的端口键值对。

写入使用下面的接口：

```cpp
template <typename T>
BT::Result setOutput(const std::string& key, const T& value);
```

| 参数 | 含义 | 本例 |
| --- | --- | --- |
| 第一个 `key` | 当前节点自己的输出端口名 | `"goal"` |
| 第二个 `value` | 要写出的 C++ 值，类型为 `T` | 保存 `"loading_area"` 的字符串变量 `goal` |

XML 会把这个输出端口连接到 Blackboard 条目；节点实现仍然只使用自己的端口名。返回值为 `BT::Result`，成功时可判真，失败时可判假并调用 `.error()` 查看原因。本篇先展示正常写入路径，下一篇会用 `written` 变量显式检查这个结果。

### 解释端口名和blackboard

Blackboard 存放数据;端口名更像“函数参数名”，数据类型是另外指定的。

拿“柜子取东西”来比喻：
- Blackboard：一个储物柜。
- Blackboard 键名：抽屉上的标签，例如 pickup_goal。
- 数据：抽屉里放的内容，例如 "loading_area"。
- 端口名：节点接收数据的接口名称，例如 goal。

看这一行 C++：

```cpp
BT::InputPort<std::string>("goal")
```

意思是：这个节点有一个叫 goal 的输入接口，接收字符串。
其中 std::string 才是类型，goal 是端口名。

再看 XML：

```xml
<NavigateToGoal goal="{pickup_goal}"/>
```

意思是：到 Blackboard 中找到标着 pickup_goal 的抽屉，把里面的数据交给这个导航节点的 goal 输入接口。

对应关系就是：

```text
Blackboard 的 pickup_goal 抽屉
里面保存 "loading_area"
          ↓ XML 指定从这里取
导航节点的 goal 输入端口
          ↓
节点知道：这次去 loading_area
```

**端口负责让节点接收或写出数据;**
**Blackboard 负责保存数据;**
**XML 负责指定它们怎么连接。**

## 保持每一步的编译、执行和路径一致

本篇各轮实践都沿用同一套框架配置、同一个可执行文件和 `trees/mission.xml`：

| 改了什么 | 接下来执行什么 |
| --- | --- |
| 第一次建立工程 | 选择 `linux-debug`，点击 Configure → Build → Launch |
| 修改 C++ 函数、类或注册代码 | 保存后点击 Build → Launch |
| 只改 XML 结构或端口配置 | 保存后再次点击 Launch |
| 修改 CMake 配置或移动工程目录 | 点击 Configure → Build → Launch |

C++ 中使用 `createTreeFromFile(BT_XML_PATH)`，实际 XML 路径由 `src/CMakeLists.txt` 根据源码目录提供。无论从工程根目录、构建目录，还是编辑器中启动，程序读取的都是源码中的 `trees/mission.xml`；只修改 XML 后重新运行即可。

这个完整路径也避免了向解析器传入不含目录部分的裸文件名。本篇的路径设置用于源码工程的开发和调试，安装发布时的资源布局后续按需处理；当前练习编译后直接运行，不要求执行安装。

本篇以 VSCode 的 CMake Tools 为操作入口：Configure 准备构建配置，Build 编译程序，Launch 直接运行，Debug 启动断点调试。不同扩展版本的按钮位置可能略有不同，以 CMake 面板中的操作名称为准；界面细节可对照 [CMakePresets与构建安装](/wiki/2023-10-05-cplusplus-jiao-xue/2200-0100-cmakepresets-yu-gou-jian-an-zhuang)。

CMake Tools 默认可能在 Launch 前自动检查并构建。只修改 XML 时，即使界面出现这一步，通常也没有 C++ 文件需要重新编译；本篇所说“直接 Launch”表示无需手动先点 Build。

本篇使用 `tickRoot()` 执行一次。所有示例节点都立即结束，因此一次根节点 tick 就足够。3.8 还有 `tickRootWhileRunning()`：先 tick 一次，如果得到 `RUNNING` 就继续驱动，直到成功或失败。持续任务如何多次 tick，后面实现导航时再实践。

引入异常报告后的两个版本中，如果将 `PrintGoal` 输入改为 `{unknown_goal}`，又没有节点写入该条目，主程序会显示读取错误并返回 `2`；未注册的节点名则会在创建树时报告错误。它们与电量不足时返回的树任务 `FAILURE` 是不同情况。
