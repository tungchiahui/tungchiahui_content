> 先运行官方实例，建立“命令确实经过控制器进入硬件插件”的证据，再自己写包。

## 示例 1：启动官方 RRBot

### 程序目标

运行两个旋转关节，查看控制器是否 active、命令接口是否 claimed，然后发送目标。

终端 1：

```bash
source /opt/ros/humble/setup.bash
source ~/ros2_control_demos_ws/install/setup.bash
ros2 launch ros2_control_demo_example_1 rrbot.launch.py gui:=false
```

先关闭自动 GUI，便于观察后台组件。需要 RViz 时，把 `gui:=false` 改为 `gui:=true`，并确保容器图形显示可用。

终端 2，source 同一个工作区后执行：

```bash
ros2 control list_controllers
ros2 control list_hardware_components
ros2 control list_hardware_interfaces
ros2 topic info /forward_position_controller/commands -v
```

### 运行输出与执行顺序

控制器列表应包含两个 active 实例：`joint_state_broadcaster` 和 `forward_position_controller`。命令接口为 `joint1/position`、`joint2/position`，应显示 available、claimed。

`available` 表示接口可以被框架使用；`claimed` 表示某个控制器已经获得该命令接口。声明在 YAML 中并不等于控制器已经加载或激活。

## 示例 2：发送位置目标并观察反馈

```bash
ros2 topic pub --once /forward_position_controller/commands \
  std_msgs/msg/Float64MultiArray "{data: [0.4, -0.2]}"
ros2 topic echo /joint_states
```

不要只看 position 数组。先对照 `name` 数组，确认哪一个值属于哪个关节。JointState 的关节排列顺序不应靠猜测。

### 本次容器实测现象

约几秒后曾采到：joint1 约 0.14036、joint2 约 -0.07018，且继续向目标靠近。这是一次运行采样，不是固定时间的精确验收值。

为什么没有立刻达到 0.4 和 -0.2？当前固定提交的硬件配置中 `example_param_hw_slowdown` 为 100；模拟 read 每轮只走剩余误差的一小部分。它不是 Gazebo 动力学，也不是串口失灵。

### 一条命令经过哪些文件

```text
rrbot.launch.py 启动 robot_state_publisher 和 ros2_control_node
  → Xacro 展开硬件描述
  → ResourceManager 加载 RRBot 硬件插件
  → spawner 加载并激活两个控制器
  → Topic 回调收到 Float64MultiArray
  → ForwardCommandController::update 写入命令接口
  → RRBot 的 read 逐渐更新模拟状态
  → broadcaster 发布 JointState
```

## 示例 3：确认 RViz 显示的依据

如果打开 RViz，选择与模型对应的 Fixed Frame，添加 RobotModel 和 TF。RViz 读取模型及 TF，不会直接读取硬件插件中的 C++ vector。

不要同时启动 `joint_state_publisher_gui` 来给同一机器人发布 `/joint_states`。它会让你无法分清显示来自硬件反馈还是手动滑块。

## 常见问题

- 没有 `/controller_manager` 服务：先看启动终端中 URDF、插件和 YAML 的报错。
- 控制器 inactive：查看接口名称、硬件状态和激活日志。
- Topic 存在却不动：确认类型、订阅者、命令数组长度，以及当前 active 的控制器。
- 反馈缓慢变化：先查看模拟参数和更新频率，不能只凭速度判断失败。
