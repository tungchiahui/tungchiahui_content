#### 扩展知识点

##### xmacro

1. 变量基本完全对应

xacro

```xml
<xacro:property name="wheel_radius" value="0.076"/>

<cylinder radius="${wheel_radius}" length="0.03"/>
```

xmacro

```xml
<xmacro_define_value name="wheel_radius" value="0.076"/>

<cylinder>
    <radius>${wheel_radius}</radius>
    <length>0.03</length>
</cylinder>
```

2. 宏定义也几乎一一对应

xacro

```xml
<xacro:macro name="wheel" params="name radius width">
    <link name="${name}">
        ...
    </link>
</xacro:macro>
```

调用：

```xml
<xacro:wheel
    name="front_left_wheel"
    radius="0.076"
    width="0.03"
/>
```

xmacro

```xml
<xmacro_define_block
    name="wheel"
    params="name radius width">

    <link name="${name}">
        ...
    </link>

</xmacro_define_block>
```

调用：

```xml
<xmacro_block
    name="wheel"
    name_arg="front_left_wheel"
    radius="0.076"
    width="0.03"
/>
```

3. include

xacro

```xml
<xacro:include filename="wheel.xacro"/>
```

xmacro

```xml
<xmacro_include uri="file://wheel.sdf.xmacro"/>
```

在当前项目中还可以看到：

```xml
<xmacro_include
    uri="model://rm25_example_robot/rm25_example_robot.def.xmacro"
/>
```

这里的`model://`是 `sdformat_tools` 针对 Gazebo / SDF 做的 URI 解析支持。

4. ${} 表达式

xmacro 和 xacro 都支持类似：

```xml
${radius}
```

以及数学表达式：

```xml
${2 * radius}
```

例如：

```xml
<ixx>${m*(y*y+z*z)/12}</ixx>
```

所以可以在宏参数中进行简单数学运算。

5. 条件

xacro

```xml
<xacro:if value="${use_lidar}">
    ...
</xacro:if>
```

xmacro

xmacro 中通常可以通过宏调用的 condition 控制：

```xml
<xmacro_block
    name="lidar"
    condition="${use_lidar}"
    ...
/>
```

条件为真时展开这个宏，条件为假时不展开。

6. .def.xmacro

例如：

```text
rm25_example_robot.def.xmacro
```

这里的`.def`并不是 xmacro 的特殊语法，只是一种文件命名习惯。

通常表示：这个文件主要负责定义宏。

类似：

```text
xxx.def.xmacro
    ↓
定义机器人结构、link、joint 等宏
```

然后：

```text
simulation_robot.sdf.xmacro
    ↓
include 前面的 def.xmacro
    ↓
调用其中定义的宏
    ↓
生成完整 SDF
```

例如以后可以写：

```text
ysu2026_sentry_robot.def.xmacro
```

里面定义：

```xml
<xmacro_define_block
    name="ysu2026_sentry_robot"
    params="chassis_height gimbal_yaw_height">

    ...

</xmacro_define_block>
```

然后在：

```xml
simulation_robot.sdf.xmacro
```

中引入并调用：

```xml
<xmacro_include
    uri="model://ysu2026_sentry_robot/ysu2026_sentry_robot.def.xmacro"
/>

<xmacro_block
    name="ysu2026_sentry_robot"
    chassis_height="${chassis_height}"
    gimbal_yaw_height="${gimbal_yaw_height}"
/>
```

记忆：

```text
xmacro_define_value
    ≈ xacro:property

xmacro_define_block
    ≈ xacro:macro

xmacro_block
    ≈ 调用 xacro macro

xmacro_include
    ≈ xacro:include

${...}
    ≈ ${...}
```


#### 总体框架

##### xmacro介绍

这个xmacro是本项目里自定义的一种格式，为了实现：

```text
                  ┌→ SDF → Gazebo
.sdf.xmacro ──────┤
                  └→ SDF → URDF → robot_state_publisher
```

而之前学过的xacro+urdf,这个项目主要是xmacro+sdf。（对比着理解）

然后我们之前接触的都是

```text
robot.urdf.xacro
      ↓
    xacro
      ↓
robot_description
      ↓
robot_state_publisher
      ↓
TF
```

而这个项目是：

```text
simulation_robot.sdf.xmacro
          ↓
      xmacro4sdf
          ↓
         SDF
       ↙     ↘
   Gazebo    sdf2urdf
                 ↓
               URDF
                 ↓
      robot_state_publisher
                 ↓
                TF
```

| 功能 | xacro | xmacro |
|---|---|---|
| 定义变量 | `<xacro:property name="r" value="0.1"/>` | `<xmacro_define_value name="r" value="0.1"/>` |
| 使用变量 | `${r}` | `${r}` |
| 数学表达式 | `${2 * r}` | `${2 * r}` |
| 定义宏 | `<xacro:macro name="wheel" params="r w">` | `<xmacro_define_block name="wheel" params="r w">` |
| 调用宏 | `<xacro:wheel r="..." w="..."/>` | `<xmacro_block name="wheel" r="..." w="..."/>` |
| include | `<xacro:include filename="xxx.xacro"/>` | `<xmacro_include uri="file://xxx.xmacro"/>` |
| 条件 | `<xacro:if value="${...}">...</xacro:if>` | 主要通过 `<xmacro_block ... condition="${...}"/>` |
| namespace | `xmlns:xacro=...` | 不需要 |
| 参数默认值等高级功能 | 较丰富 | 简化很多 |

##### 修改机器人参数

主要是机器人的**底盘长宽、轮距/轴距、轮径、云台高度、Mid360 安装位置**：

```text
1. 底盘长宽高 / collision
2. 四个轮子的位置
3. 轮子半径
4. chassis_height
5. gimbal_yaw_height
6. gimbal_pitch_height
7. Mid360 的 parent 和 pose
```

首先你得知道ROS默认规定的方向：

```text
+x：车头方向
+y：车体左侧
+z：竖直向上
```

```text
+roll：绕x轴逆时针
+pitch：绕y轴逆时针
+yaw：绕z轴逆时针
```

角度正方向则统一遵守`右手定则`：
如果你站在每根轴的正方向一端，朝原点看，那么正旋转看起来都是逆时针。
所以对于机器人坐标系，可以更直观地记：
- +yaw：车头向左转。
- +pitch：车头向下压。
- +roll：左侧抬高、右侧降低。


而且北极熊现在的模型里，base_footprint 在地面，chassis 原点基本位于四个轮子的轮轴中心高度。

| 参数 | 你实际应该量什么 | 当前代码含义 |
|---|---|---|
| 底盘长度 | 车体刚性主体前沿到后沿，沿 X | `geometry_box x=...` |
| 底盘宽度 | 车体刚性主体左沿到右沿，沿 Y | `geometry_box y=...` |
| 底盘高度 | 刚性主体底面到顶面，沿 Z | `geometry_box z=...` |
| 轴距 | 前轮轴心到后轮轴心的 X 向距离 | `x_front - x_rear` |
| 轮距 | 左轮中心面到右轮中心面的 Y 向距离 | `y_left - y_right` |
| 轮径 | 轮子外圆直径 | 当前 `2 × 0.0758` |
| `chassis_height` | 地面 → `chassis` 坐标系原点 | 当前 0.076 m |
| `gimbal_yaw_height` | `chassis` 原点 → 云台 yaw 旋转轴原点 | 当前 0.1376 m |
| `gimbal_pitch_height` | yaw 轴原点 → pitch 轴原点 | 当前 0.16 m |
| Mid360 `pose` | parent 坐标系原点 → `front_mid360` 原点 | 当前相对 `chassis` |

1. ysu2026_sentry_robot.def.xmacro    ← 机器人“本体结构”的唯一真源
2. reality_robot.sdf.xmacro           ← 实车入口：传感器安装、实车专用高度/姿态
3. simulation_robot.sdf.xmacro        ← 仿真入口：仿真传感器和 Gazebo 插件
4. model.sdf.xmacro                   ← rmoss_gz_resources 里的 standalone Gazebo 模型入口

3. 轴距和轮距也要量“轮中心”，不是底盘外壳

北极熊的是：

```xml
        <!--front_left wheel link and joint-->
        <xmacro_block name="chassis_wheel_l" prefix="front_left" parent="chassis" pose="0.207 0.194 0 0 0 0"/>
        <!--front_right wheel link and joint-->
        <xmacro_block name="chassis_wheel_r" prefix="front_right" parent="chassis" pose="0.207 -0.194 0 0 0 0"/>
        <!--rear_left wheel link and joint-->
        <xmacro_block name="chassis_wheel_r" prefix="rear_left" parent="chassis" pose="-0.207 0.194 0 0 0 0"/>
        <!--rear_right wheel link and joint-->
        <xmacro_block name="chassis_wheel_l" prefix="rear_right" parent="chassis" pose="-0.207 -0.194 0 0 0 0"/>
```

```text
FL:  0.207   0.194
FR:  0.207  -0.194
RL: -0.207   0.194
RR: -0.207  -0.194
```

那么轴距是 = 0.207 - (-0.207) = 0.414 m

那么轮距是 = 0.194 - (-0.194) = 0.388 m

示意图：

```text
                 +X 前

       FL ●────────────● FR
          │            │
          │            │
          │            │
          │            │
       RL ●────────────● RR

          ←  轮距  →

前后两个轮轴中心的距离
        = 轴距
```

所以要测量的数据是：
前左轮中心 到 后左轮中心：X 方向距离
左轮中心面 到 右轮中心面：Y 方向距离
不是量轮胎最外侧。

   2. mid360的pose

    ```xml
        parent="chassis"
    ```

    - 他的雷达是装在底盘上的，所以`parent="chassis"`，如果雷达要装在云台，就改成`parent="gimbal_yaw"`，那么偏移也会变成相对于`gimbal_yaw` 坐标系的偏移。.

    ```text
    x = +0.16 m
    y =  0
    ```

    ```text
    向前 160 mm
    左右不偏
    向上 180 mm
    ```

    ```text
    pitch = 0°
    yaw   = π/2 = 90°
    ```

## 数据对接

### Linux到MCU的数据

导航这边主要是下发cmd_vel相关的数据,主要包含vx,vy,wz。这里的wz是wz_navigation，而最终机器人自旋速度是`wz_final = wz_navigation + wz_spin;`（最终自旋速度 = 导航速度 + 自旋速度）

而北极熊导航这边是由上位机决定的自旋速度

```yaml
fake_vel_transform:
  ros__parameters:
    input_cmd_vel_topic: "cmd_vel_nav2_result"
    output_cmd_vel_topic: "cmd_vel"
    cmd_spin_topic: "cmd_spin"
    init_spin_speed: 3.14
```

这里表示，他把nav2最后给的速度话题设置成了`cmd_vel_nav2_result`，而经过这个节点融合了自旋速度最后生成了`cmd_vel`，里面的`wz`就是`wz_final`。


### MCU到Linux的数据

#### 总概

```text
chassis
  │
  ├─ gimbal_yaw_odom_joint      绕 Z，可动
  ▼
gimbal_yaw_odom
  │
  ├─ gimbal_pitch_odom_joint    fixed
  ▼
gimbal_pitch_odom
  │
  ├─ gimbal_yaw_joint           绕 Z，可动
  ▼
gimbal_yaw
  │
  ├─ gimbal_pitch_joint         绕 Y，可动
  ▼
gimbal_pitch
```

北极熊官方导航 README 明确把实车串口提供的关节称为：

```text
gimbal_yaw_odom   = 大 yaw
gimbal_yaw        = 小 yaw
gimbal_pitch      = pitch
```

gimbal_pitch_odom_joint：可以认为就是 0，因为你现在的 description 里它本来就是 fixed。
gimbal_yaw_odom_joint：上电那一刻可以是 0，但运行时不能固定为 0，前提是咱们有北极熊同样的“大 yaw”机构。它应该跟着大 yaw 的真实角度更新。


| joint | 当前模型类型 | 北极熊代码里填的数据 | 可以理解成 |
|---|---|---|---|
| `gimbal_yaw_odom_joint` | revolute | `ReceiveJointState.yaw` | 云台/IMU 的**参考 yaw 相对 chassis** |
| `gimbal_pitch_odom_joint` | **fixed** | `ReceiveJointState.pitch` | 参考 pitch 层，但当前模型实际上固定 |
| `gimbal_yaw_joint` | revolute | IMU `yaw` | IMU 相对于参考姿态的 yaw |
| `gimbal_pitch_joint` | revolute | IMU `pitch` | IMU 相对于参考姿态的 pitch |


北极熊官方 standard_robot_pp_ros2 实际上有两类 MCU→Linux 数据。

第一类是 IMU 数据：

yaw，pitch，roll然后Linux 收到以后，发布 `sensor_msgs/msg/Imu`。

但其实这个数据没啥用，北极熊并没在导航里用到roll,rpy_vel这些数据。

```text
imu_state

roll       rad
pitch      rad
yaw        rad

roll_vel   rad/s
pitch_vel  rad/s
yaw_vel    rad/s
```

然后
pitch → gimbal_pitch_joint
yaw   → gimbal_yaw_joint

第二类是 JointState/云台参考位置数据：

这个很重要

```text
joint_state

pitch_odom   rad
yaw_odom     rad
```

Linux 收到以后并不马上发布，而是保存：

```cpp
last_gimbal_pitch_odom_joint_ = pitch_odom;
last_gimbal_yaw_odom_joint_   = yaw_odom;
```

下一次 IMU 数据到来时，北极熊一次发布完整四项：

```cpp
joint_msg.name = {
    "gimbal_pitch_joint",
    "gimbal_yaw_joint",
    "gimbal_pitch_odom_joint",
    "gimbal_yaw_odom_joint",
};

joint_msg.position = {
    imu_pitch,
    imu_yaw,
    pitch_odom,
    yaw_odom,
};
```

但是咱们没有大小yaw结构的话：

但为了尽量不改北极熊后面的 TF / Nav2 框架，最合适的兼容方法是：

```text
你们真实 yaw
    ↓
gimbal_yaw_odom_joint

不存在的小 yaw
    ↓
gimbal_yaw_joint = 0

你们真实 pitch
    ↓
gimbal_pitch_joint
```

```text
chassis
  │
  │ gimbal_yaw_odom_joint = 实际 yaw（大yaw）
  ▼
gimbal_yaw_odom
  │
  │ gimbal_pitch_odom_joint = fixed
  ▼
gimbal_pitch_odom
  │
  │ gimbal_yaw_joint = 0 (不存在小yaw)
  ▼
gimbal_yaw
  │
  │ gimbal_pitch_joint = 实际 pitch
  ▼
gimbal_pitch
```

```cpp
      msg_jointstate.name = {
          "gimbal_pitch_joint",      // 小pitch
          "gimbal_yaw_joint",        //小yaw
          "gimbal_pitch_odom_joint",   //fixed
          "gimbal_yaw_odom_joint"    //大yaw
      };

      msg_jointstate.position = {
                      pitch,   // 真实 pitch
                      0.0,     // 不存在的小 yaw
                      0.0,     // fixed
                      yaw      // 真实 yaw
      };
```

```text
chassis
  │
  │ gimbal_yaw_odom_joint   ← 大 yaw，动态
  ▼
gimbal_yaw_odom
  │
  │ gimbal_pitch_odom_joint ← fixed
  ▼
gimbal_pitch_odom
  │
  │ gimbal_yaw_joint        ← 小 yaw，动态
  ▼
gimbal_yaw
  │
  │ gimbal_pitch_joint      ← pitch，动态
  ▼
gimbal_pitch
```

最后 `chassis → gimbal_yaw` 依然完全正确。

综上，咱们正真需要的是：

```text
MCU → Linux

roll       rad
pitch      rad
yaw        rad
joint_yaw  rad
joint_pitch rad
```

其中云台 IMU 的 RPY 用来生成 `/serial/imu` 的 orientation。

云台电机返回的角度用来`joint_yaw`和`joint_pitch`。

但其实，如果你的雷达放在Yaw的云台上，其实joint_pitch无所谓，不影响最终的导航，但可能和自瞄有关系。

咱们需要跟MCU规定好，他需要把云台电机的角度进行转换：
- 云台朝底盘正方向时为0
- 范围必须归一化，`[-π, π) rad`，也就是 `[-180°, 180°)`
- 旋转方向按照标准坐标系，也就是在某个轴的正方向看，绕他的逆时针为正。


查看`sensor_msgs/msg/JointState`：

```bash
ros2 interface show sensor_msgs/msg/JointState
```

```text
#
# The state of each joint (revolute or prismatic) is defined by:

#
```

这个`sensor_msgs/msg/JointState`里的数据主要用于搭配`robot_description`来发布动态TF。

比如：

```xml
    <parent>chassis</parent>
    <child>gimbal_yaw_odom</child>
    <axis>
        <xyz>0 0 1</xyz>
    </axis>
</joint>
```

```text
父坐标系：chassis
子坐标系：gimbal_yaw_odom
转轴：+Z
```

然后咱们发

```cpp
name = "gimbal_yaw_odom_joint";
position = joint_yaw;
```

robot_state_publisher 就自动算：

```text
chassis
   ↓ joint_yaw
gimbal_yaw_odom
```

并发布动态 TF。

```text
STM32
├── joint_yaw
├── joint_pitch
│
│
▼
serial_comm
│
└── /serial/gimbal_joint_state
          ↓
joint_state_publisher
          ↓
     /joint_states
          ↓
robot_state_publisher
          ↓
        /**tf**
```


#### 这些变量的范围和方向

至于这些角到底怎么定义，重点不是 IMU 的世界系 RPY，而是 joint 自己的坐标轴和零位。

yaw这里：

```xml
<xyz>0 0 1</xyz>
```

所以 yaw 是绕父坐标系的 +Z 转。
ROS 采用右手系：

```text
X 前
Y 左
Z 上
```

从机器人上方往下看：

```text
joint_yaw > 0
```

一般就是逆时针转，也就是向左转。
所以建议你下位机定义：
云台正对底盘 X+ 前方：

```text
joint_yaw = 0

向左转：
joint_yaw > 0

向右转：
joint_yaw < 0
```

例如：

```text
正前方      0 rad
左 90°      +π/2
右 90°      -π/2
后方        ±π
```

这个和 ROS 的右手系最自然。

出现问题，雷达的hz特别的小：

这个现象很像不是 Mid360 真掉到 3 Hz，而是 RELIABLE 大点云被远端订阅者拖慢了。
这版驱动的 /livox/lidar/pointcloud publisher 是默认 QoS，也就是你前面看到的那种 RELIABLE。一帧约 257 KB，20 Hz 单独 PointCloud2 就约 41 Mb/s。ROS 2 的 DDS/QoS 本身支持不同可靠性策略；对这类高频传感器数据，让显示/调试端用“允许丢旧帧、优先拿最新帧”的方式通常更合适。ROS Documentation
而且一个慢的远程 RELIABLE reader，可能让 writer 做重传、排队甚至产生反压。于是你会看到一个很反直觉的现象

```text
电脑/RViz 收得慢
       ↓
RELIABLE 重传/积压
       ↓
工控机 publisher 也被拖住
       ↓
连工控机本地 ros2 topic hz 看起来都只剩 3 Hz
```

把电脑上的 RViz、ros2 topic echo、ros2 topic hz 全部关掉。

重启工控机上的驱动一般即可解决。

## 参数

### SLAM

SLAM之前需要先调俩参数

#### gravity与gravity_init

咱们的mid360是roll = -π/4 = -45°安装的。

方法一：理论计算法（适用于实物和仿真）

机器人静止时，IMU 的 linear_acceleration 本质上测的是与重力反向的“比力”。如果只绕 X 轴 roll 一个角度 r，那么静止时大致有：

```text
ax = 0
ay = g·sin(r)
az = g·cos(r)
```


```text
g = 9.81 m/s²
r = +45°


ax = 0

ay = 9.81 × sin(-45°)
   ≈ -6.9367

az = 9.81 × cos(-45°)
   ≈ +6.9367
```

##### 仿真

方法二：测量法

仿真环境下imu测量：

```bash
ros2 topic echo /red_standard_robot1/livox/imu --once
```

```text

  x: 1.877548187489191e-05
  y: -6.929646440459081
  z: 6.929646470797371
```

##### 实物

方法二：测量法



```text
平均 linear_acceleration ≈
x = 0.00424
y = 0.71589

```

通过计算可知`atan2(0.716, 0.696) ≈ 45.8°`，实际上经过`安装加工误差，雷达支架误差,地面是否完全水平,车体自身倾斜,IMU 零偏`等一系列误差，和理论值有点出入很正常。

下面是`Point-LIO`代码：

```cpp
tmp_gravity =
    -mean_acc / mean_acc.norm() * G_m_s2;
```

就是三步：先求平均加速度 → 求这个向量的模 → 归一化后取反。

先求平均加速度mean_acc = [0.00423894,0.71588876,0.69592434]
再求这个mean_acc的模，mean_acc.norm() =sqrt(0.00423894²+ 0.71588876²+ 0.69592434²) ≈ 0.99841142 ≈ 1.0
G_m_s2 ≈ 1.0 g （mid360实物的单位是g，而Gazebo IMU里的单位是m/s²主要还是通过测量法，看模是接近1.0还是9.81）
所以代入公式得[0.00425, 0.71703, 0.69703]，公式里有个负号，取反后得出[-0.00425, -0.71703, -0.69703]
