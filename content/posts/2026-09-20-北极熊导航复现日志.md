#### 扩展知识点

##### xmacro

1. 变量基本完全对应

xacro

```xml
<xacro:property name="wheel_radius" value="0.076"/>

<cylinder radius="${wheel_radius}" length="0.03"/>
```

xmacro

```xml
<xmacro_define_value name="wheel_radius" value="0.076"/>

<cylinder>
    <radius>${wheel_radius}</radius>
    <length>0.03</length>
</cylinder>
```

2. 宏定义也几乎一一对应

xacro

```xml
<xacro:macro name="wheel" params="name radius width">
    <link name="${name}">
        ...
    </link>
</xacro:macro>
```

调用：

```xml
<xacro:wheel
    name="front_left_wheel"
    radius="0.076"
    width="0.03"
/>
```

xmacro

```xml
<xmacro_define_block
    name="wheel"
    params="name radius width">

    <link name="${name}">
        ...
    </link>

</xmacro_define_block>
```

调用：

```xml
<xmacro_block
    name="wheel"
    name_arg="front_left_wheel"
    radius="0.076"
    width="0.03"
/>
```

3. include

xacro

```xml
<xacro:include filename="wheel.xacro"/>
```

xmacro

```xml
<xmacro_include uri="file://wheel.sdf.xmacro"/>
```

在当前项目中还可以看到：

```xml
<xmacro_include
    uri="model://rm25_example_robot/rm25_example_robot.def.xmacro"
/>
```

这里的`model://`是 `sdformat_tools` 针对 Gazebo / SDF 做的 URI 解析支持。

4. ${} 表达式

xmacro 和 xacro 都支持类似：

```xml
${radius}
```

以及数学表达式：

```xml
${2 * radius}
```

例如：

```xml
<ixx>${m*(y*y+z*z)/12}</ixx>
```

所以可以在宏参数中进行简单数学运算。

5. 条件

xacro

```xml
<xacro:if value="${use_lidar}">
    ...
</xacro:if>
```

xmacro

xmacro 中通常可以通过宏调用的 condition 控制：

```xml
<xmacro_block
    name="lidar"
    condition="${use_lidar}"
    ...
/>
```

条件为真时展开这个宏，条件为假时不展开。

6. .def.xmacro

例如：

```text
rm25_example_robot.def.xmacro
```

这里的`.def`并不是 xmacro 的特殊语法，只是一种文件命名习惯。

通常表示：这个文件主要负责定义宏。

类似：

```text
xxx.def.xmacro
    ↓
定义机器人结构、link、joint 等宏
```

然后：

```text
simulation_robot.sdf.xmacro
    ↓
include 前面的 def.xmacro
    ↓
调用其中定义的宏
    ↓
生成完整 SDF
```

例如以后可以写：

```text
ysu2026_sentry_robot.def.xmacro
```

里面定义：

```xml
<xmacro_define_block
    name="ysu2026_sentry_robot"
    params="chassis_height gimbal_yaw_height">

    ...

</xmacro_define_block>
```

然后在：

```xml
simulation_robot.sdf.xmacro
```

中引入并调用：

```xml
<xmacro_include
    uri="model://ysu2026_sentry_robot/ysu2026_sentry_robot.def.xmacro"
/>

<xmacro_block
    name="ysu2026_sentry_robot"
    chassis_height="${chassis_height}"
    gimbal_yaw_height="${gimbal_yaw_height}"
/>
```

记忆：

```text
xmacro_define_value
    ≈ xacro:property

xmacro_define_block
    ≈ xacro:macro

xmacro_block
    ≈ 调用 xacro macro

xmacro_include
    ≈ xacro:include

${...}
    ≈ ${...}
```


#### 总体框架

##### xmacro介绍

这个xmacro是本项目里自定义的一种格式，为了实现：

```text
                  ┌→ SDF → Gazebo
.sdf.xmacro ──────┤
                  └→ SDF → URDF → robot_state_publisher
```

而之前学过的xacro+urdf,这个项目主要是xmacro+sdf。（对比着理解）

然后我们之前接触的都是

```text
robot.urdf.xacro
      ↓
    xacro
      ↓
robot_description
      ↓
robot_state_publisher
      ↓
TF
```

而这个项目是：

```text
simulation_robot.sdf.xmacro
          ↓
      xmacro4sdf
          ↓
         SDF
       ↙     ↘
   Gazebo    sdf2urdf
                 ↓
               URDF
                 ↓
      robot_state_publisher
                 ↓
                TF
```

| 功能 | xacro | xmacro |
|---|---|---|
| 定义变量 | `<xacro:property name="r" value="0.1"/>` | `<xmacro_define_value name="r" value="0.1"/>` |
| 使用变量 | `${r}` | `${r}` |
| 数学表达式 | `${2 * r}` | `${2 * r}` |
| 定义宏 | `<xacro:macro name="wheel" params="r w">` | `<xmacro_define_block name="wheel" params="r w">` |
| 调用宏 | `<xacro:wheel r="..." w="..."/>` | `<xmacro_block name="wheel" r="..." w="..."/>` |
| include | `<xacro:include filename="xxx.xacro"/>` | `<xmacro_include uri="file://xxx.xmacro"/>` |
| 条件 | `<xacro:if value="${...}">...</xacro:if>` | 主要通过 `<xmacro_block ... condition="${...}"/>` |
| namespace | `xmlns:xacro=...` | 不需要 |
| 参数默认值等高级功能 | 较丰富 | 简化很多 |

##### 修改机器人参数

主要是机器人的**底盘长宽、轮距/轴距、轮径、云台高度、Mid360 安装位置**：

```text
1. 底盘长宽高 / collision
2. 四个轮子的位置
3. 轮子半径
4. chassis_height
5. gimbal_yaw_height
6. gimbal_pitch_height
7. Mid360 的 parent 和 pose
```

首先你得知道ROS默认规定的方向：

```text
+x：车头方向
+y：车体左侧
+z：竖直向上
```

```text
+roll：绕x轴逆时针
+pitch：绕y轴逆时针
+yaw：绕z轴逆时针
```

角度正方向则统一遵守`右手定则`：
如果你站在每根轴的正方向一端，朝原点看，那么正旋转看起来都是逆时针。
所以对于机器人坐标系，可以更直观地记：
- +yaw：车头向左转。
- +pitch：车头向下压。
- +roll：左侧抬高、右侧降低。


而且北极熊现在的模型里，base_footprint 在地面，chassis 原点基本位于四个轮子的轮轴中心高度。

| 参数 | 你实际应该量什么 | 当前代码含义 |
|---|---|---|
| 底盘长度 | 车体刚性主体前沿到后沿，沿 X | `geometry_box x=...` |
| 底盘宽度 | 车体刚性主体左沿到右沿，沿 Y | `geometry_box y=...` |
| 底盘高度 | 刚性主体底面到顶面，沿 Z | `geometry_box z=...` |
| 轴距 | 前轮轴心到后轮轴心的 X 向距离 | `x_front - x_rear` |
| 轮距 | 左轮中心面到右轮中心面的 Y 向距离 | `y_left - y_right` |
| 轮径 | 轮子外圆直径 | 当前 `2 × 0.0758` |
| `chassis_height` | 地面 → `chassis` 坐标系原点 | 当前 0.076 m |
| `gimbal_yaw_height` | `chassis` 原点 → 云台 yaw 旋转轴原点 | 当前 0.1376 m |
| `gimbal_pitch_height` | yaw 轴原点 → pitch 轴原点 | 当前 0.16 m |
| Mid360 `pose` | parent 坐标系原点 → `front_mid360` 原点 | 当前相对 `chassis` |

1. ysu2026_sentry_robot.def.xmacro    ← 机器人“本体结构”的唯一真源

北极熊的是：

```xml

        <!--front_right wheel link and joint-->

        <!--rear_left wheel link and joint-->
        <xmacro_block name="chassis_wheel_r" prefix="rear_left" parent="chassis" pose="-0.207 0.194 0 0 0 0"/>
        <!--rear_right wheel link and joint-->
        <xmacro_block name="chassis_wheel_l" prefix="rear_right" parent="chassis" pose="-0.207 -0.194 0 0 0 0"/>
```

```text
FL:  0.207   0.194
FR:  0.207  -0.194
RL: -0.207   0.194
RR: -0.207  -0.194
```

那么轴距是 = 0.207 - (-0.207) = 0.414 m

那么轮距是 = 0.194 - (-0.194) = 0.388 m

示意图：

```text
                 +X 前

       FL ●────────────● FR
          │            │
          │            │
          │            │
          │            │
       RL ●────────────● RR

          ←  轮距  →

前后两个轮轴中心的距离
        = 轴距
```

所以要测量的数据是：
前左轮中心 到 后左轮中心：X 方向距离
左轮中心面 到 右轮中心面：Y 方向距离
不是量轮胎最外侧。

    而内置 IMU 芯片相对于这个点云坐标系的位置是：

    ```text
    x = +11.00 mm
    y = +23.29 mm
    z = -44.12 mm
    ```

    ![](https://cdn.tungchiahui.cn/tungwebsite/assets/images/2026/09/20/1790078332238-5fadb21a.webp)

    ```text
    front_mid360 = LiDAR 点云 O 点
            ●
            │
            │  (+11, +23.29, -44.12) mm
            │
            ● IMU 芯片原点
    ```

    这里先提前说明下``front_mid360`就是雷达的O_XYZ原点，具体怎么推出来的，请往下看。


   2. mid360的pose

    ```xml
    <!--livox-->
    <xmacro_block
        name="livox"
        prefix="front_"
        parent="chassis"
        pose="0.16 0.0 0.18 ${pi/6} 0.0 ${pi/2}"
        ...
    />
    ```

    - 这个 pose 是 ： chassis 坐标系 → front_mid360 坐标系
    - 按北极熊这个来，是严格相对于 chassis 原点。
    - 他的雷达是装在底盘上的，所以`parent="chassis"`，如果雷达要装在云台，就改成`parent="gimbal_yaw"`，那么偏移也会变成相对于`gimbal_yaw` 坐标系的偏移。.

    ```text
    x = +0.16 m
    y =  0
    z = +0.18 m
    ```

    意思是 Mid360 O原点相对于 chassis 原点：

    ```text
    向前 160 mm
    左右不偏
    向上 180 mm
    ```

    他这里pose的后三个参数是RPY,也就是相对于chassis 原点的偏移：

    ```text
    roll  = π/6 = 30°
    pitch = 0°
    yaw   = π/2 = 90°
    ```

    经过测量，只有roll偏了40度，也就是`${2*pi/9}`

    另外你在 Mid360 model 里还会看到：

    ```xml
    <visual>
        <pose>0 0 0 0 0 ${pi}</pose>
    ```

    这个只是外观 mesh 转了 180°，不等于雷达传感器 frame 转了 180°。不要拿这个来算 TF。

    1. mid360到底量它外壳哪个点？

    这里还要再精确一层。
    北极熊当前 Mid360 模型内部是：

    ```xml
    <joint ...>
        <child>${prefix}mid360</child>
    </joint>

    <link name="${prefix}mid360">
    ```

    这里的`${prefix}mid360`会被解析为`front_mid360`：

    **这个`front_mid360`一直很懵逼，他到底是什么？**
    他在readme里写的仿真里是简化的，所以不要在仿真里反推这个坐标系的原点到底是什么？
    在reality的Point LIO里你可以看到`extrinsic_T: [-0.011, -0.02329, 0.04412]`，这正是官方IMU的偏移。
    而`frame_id = front_mid360`，所以说，反推出来`front_mid360`是我们点云的坐标系，也就是O_XYZ.

    而北极熊的 LiDAR 光学/扫描传感器实际上还额外：

    ```xml
    <sensor name="${prefix}mid360_lidar" ...>
    <pose>0 0 0.03 0 0 0</pose>
    ```

    ```text
    front_mid360 link 原点
            │
            │ +30 mm
            ▼
    LiDAR 扫描原点
    ```

    而 IMU：

    ```xml
    <sensor name="${prefix}mid360_imu" type="imu">
    ```

    没有额外 pose，所以当前仿真里基本相当于：IMU 原点 = front_mid360 原点

    2. mid360最后各个数据究竟填什么？

    `front_mid360`为mid360的O_XYZ的原点。

    那么Mid360官方点云原点就和O_XYZ原点重合。
    那么Mid360官方IMU原点就和O_XYZ有(+11, +23.29, -44.12)mm的偏移量。（但这里没必要给pose,在point_lio里给pose即可）

    所以

    ```xml
    <!-- chassis -> Mid360 官方点云 O -->
    <xmacro_block
        name="livox"
        prefix="front_"
        parent="chassis"
        pose="实际 x 实际 y 实际 z 实际 roll 实际 pitch 实际 yaw"
    />
    ```

    然后 Mid360 仿真内部：

    ```xml
    <sensor name="${prefix}mid360_lidar" type="gpu_lidar">
    <pose>0 0 0 0 0 0</pose>
    ```

    而IMU这边，北极熊的方案我看懂了，虽然他让IMU坐标系与点云坐标系直接重合，并且仿真里也是重合的。
    而在reality里，他是`extrinsic_T: [-0.011, -0.02329, 0.04412]`，这里明显是已经考虑到了这个偏移，所以我们没必要修改IMU的坐标系偏移。

### Linux到MCU的数据

导航这边主要是下发cmd_vel相关的数据,主要包含vx,vy,wz。这里的wz是wz_navigation，而最终机器人自旋速度是`wz_final = wz_navigation + wz_spin;`（最终自旋速度 = 导航速度 + 自旋速度）

而北极熊导航这边是由上位机决定的自旋速度

```yaml
fake_vel_transform:
  ros__parameters:
    input_cmd_vel_topic: "cmd_vel_nav2_result"
    output_cmd_vel_topic: "cmd_vel"
    cmd_spin_topic: "cmd_spin"
    init_spin_speed: 3.14
```

这里表示，他把nav2最后给的速度话题设置成了`cmd_vel_nav2_result`，而经过这个节点融合了自旋速度最后生成了`cmd_vel`，里面的`wz`就是`wz_final`。

所以我们给下位机下发的是vx,vy,wz_final。

### MCU到Linux的数据

#### 总概

北极熊原版本（大小Yaw）

```text
chassis
  │
  ├─ gimbal_yaw_odom_joint      绕 Z，可动
  ▼
gimbal_yaw_odom
  │
  ├─ gimbal_pitch_odom_joint    fixed
  ▼
gimbal_pitch_odom
  │
  ├─ gimbal_yaw_joint           绕 Z，可动
  ▼
gimbal_yaw
  │
  ├─ gimbal_pitch_joint         绕 Y，可动
  ▼
gimbal_pitch
```

北极熊官方导航 README 明确把实车串口提供的关节称为：

```text
gimbal_yaw_odom   = 大 yaw
gimbal_yaw        = 小 yaw
gimbal_pitch      = pitch
```

gimbal_pitch_odom_joint：可以认为就是 0，因为你现在的 description 里它本来就是 fixed。
gimbal_yaw_odom_joint：上电那一刻可以是 0，但运行时不能固定为 0，前提是咱们有北极熊同样的“大小 yaw”机构。它应该跟着大 yaw 的真实角度更新。

但是咱们没有大小Yaw结构。

| joint | 当前应填的数据 | 相对于谁 |
|---|---|---|
| `gimbal_pitch_joint` | `rel_pitch` | 实际 pitch 机构相对 yaw 机构 |
| `gimbal_yaw_joint` | `0.0` | 第二级 yaw；你们不使用它的运动 |
| `gimbal_pitch_odom_joint` | `0.0`，也可省略 | 固定连接，动态角度不起作用 |
| `gimbal_yaw_odom_joint` | `rel_yaw` | 唯一 yaw 机构相对底盘 `chassis` |


北极熊官方 standard_robot_pp_ros2 实际上有两类 MCU→Linux 数据。

| 问题 | 对应数据 |
|---|---|
| 云台在世界里朝哪里？ | 世界姿态，例如云台 IMU yaw、导航算出的云台航向 |
| 云台与底盘之间转了多少？ | yaw 机械相对角，填入对应 JointState |
| 机器人往哪个方向移动？ | 按约定参考系表达的 `vx，vy`，可以是云台方向 |

因为底盘要一直小陀螺状态，所以推断一下：

| 状态 | 云台世界朝向 | 底盘世界朝向 | 云台相对底盘角 |
|---|---:|---:|---:|
| 初始 | 0° | 0° | 0° |
| 底盘转过 90° | 0° | 90° | −90° |
| 底盘转过 180° | 0° | 180° | −180° |

| 输入机械 yaw | 导航还原的底盘世界 yaw | 导航中的云台 yaw |
|---:|---:|---:|
| `0` | `0` | `0` |
| `−π/2` | `+π/2` | `0` |
| `−π` | `π` | `0` |


而 JointState 记录 0° → −90° → −180°，是为了告诉 TF：底盘与云台的相对关系正在变化。

```text
导航/串口 vx、vy：按云台方向表达
串口 wz：最终底盘转速

JointState yaw：云台相对底盘的机械角
JointState pitch：实际 pitch 的机械相对角

云台 IMU RPY：单独保留世界/惯性姿态语义
```


第一类是 IMU 数据：

yaw，pitch，roll然后Linux 收到以后，发布 `sensor_msgs/msg/Imu`。

但其实这个数据没啥用，北极熊并没在导航里用到roll,rpy_vel这些数据。

```text
imu_state

roll       rad
pitch      rad
yaw        rad

roll_vel   rad/s
pitch_vel  rad/s
yaw_vel    rad/s
```

然后
pitch → gimbal_pitch_joint
yaw   → gimbal_yaw_joint

第二类是 JointState/云台参考位置数据：

这个很重要

```text
joint_state

pitch_odom   rad
yaw_odom     rad
```

Linux 收到以后并不马上发布，而是保存：

```cpp
last_gimbal_pitch_odom_joint_ = pitch_odom;
last_gimbal_yaw_odom_joint_   = yaw_odom;
```

下一次 IMU 数据到来时，北极熊一次发布完整四项：

```cpp
joint_msg.name = {
    "gimbal_pitch_joint",
    "gimbal_yaw_joint",
    "gimbal_pitch_odom_joint",
    "gimbal_yaw_odom_joint",
};

joint_msg.position = {
    imu_pitch,
    imu_yaw,
    pitch_odom,
    yaw_odom,
};
```

但是咱们没有大小yaw结构的话：

但为了尽量不改北极熊后面的 TF / Nav2 （因为这是为了发布TF而用的角度）框架，最合适的兼容方法是：

```text
你们真实 yaw
    ↓
gimbal_yaw_odom_joint

不存在的小 yaw
    ↓
gimbal_yaw_joint = 0

你们真实 pitch
    ↓
gimbal_pitch_joint
```

```text
chassis
  │
  │ gimbal_yaw_odom_joint = 实际 yaw（大yaw）
  ▼
gimbal_yaw_odom
  │
  │ gimbal_pitch_odom_joint = fixed
  ▼
gimbal_pitch_odom
  │
  │ gimbal_yaw_joint = 0 (不存在小yaw)
  ▼
gimbal_yaw
  │
  │ gimbal_pitch_joint = 实际 pitch
  ▼
gimbal_pitch
```

```cpp
      msg_jointstate.name = {
          "gimbal_pitch_joint",      // 小pitch
          "gimbal_yaw_joint",        //小yaw
          "gimbal_pitch_odom_joint",   //fixed
          "gimbal_yaw_odom_joint"    //大yaw
      };

      msg_jointstate.position = {
                static_cast<fp64>(rel_pitch),  // 唯一机械 pitch
                static_cast<fp64>(rel_yaw),    // 唯一机械 yaw
                0.0,                          // 固定层
                0.0                           // 固定层
      };
```

```text
chassis
  │
  │ gimbal_yaw_odom_joint   ← 大 yaw，动态改为静态（也给fixed掉）
  ▼
gimbal_yaw_odom
  │
  │ gimbal_pitch_odom_joint ← fixed
  ▼
gimbal_pitch_odom
  │
  │ gimbal_yaw_joint        ← 小 yaw，动态
  ▼
gimbal_yaw
  │
  │ gimbal_pitch_joint      ← pitch，动态
  ▼
gimbal_pitch
```

最后 `chassis → gimbal_yaw` 依然完全正确。

综上，咱们正真需要的是：

```text
MCU → Linux

roll       rad
pitch      rad
yaw        rad
joint_yaw  rad
joint_pitch rad
```

其中云台 IMU 的 RPY 用来生成 `/serial/imu` 的 orientation。

云台电机返回的角度用来`joint_yaw`和`joint_pitch`。

但其实，如果你的雷达放在Yaw的云台上，其实joint_pitch无所谓，不影响最终的导航，但可能和自瞄有关系。

单位、方向和零位，可以从当前模型推出：

| 项目 | 当前 ROS 模型的约定 |
|---|---|
| 单位 | **rad**；串口节点不会自动把度转成弧度 |
| yaw 正方向 | 从车顶往下看，**逆时针为正** |
| yaw 零位 | 云台前向与底盘前向对齐 |
| pitch 正方向 | **向下俯为正，向上仰为负** |
| pitch 零位 | pitch 机构与 yaw 层坐标轴对齐；不代表坡地时相对世界水平 |


咱们需要跟MCU规定好，他需要把云台电机的角度进行转换：
- 云台朝底盘正方向时为0
- 范围必须归一化，`[-π, π) rad`，也就是 `[-180°, 180°)`
- 旋转方向按照标准坐标系，也就是在某个轴的正方向看，绕他的逆时针为正。

然后pitch_odom要进行限幅：

```xml
<joint name="gimbal_pitch_joint" type="revolute">
    ...
    <axis>
        <xyz>0 1 0</xyz>
        <limit>
            <effort>100</effort>
            <lower>${-3.14*0.25}</lower>
            <upper>${3.14*0.18}</upper>
            <velocity>50</velocity>
        </limit>
    </axis>
</joint>
```

如果规定机械水平位是0的话，目前：
- lower：约 −45°，向上仰。
- upper：约 +32.4°，向下俯。
单位都是 rad。

这里只是会限制ROS2里Gazebo的限幅。（真正的限幅应该让MCU端根据机械限位进行限位）

#### 这些变量的范围和方向

至于这些角到底怎么定义，重点不是 IMU 的世界系 RPY，而是 joint 自己的坐标轴和零位。

yaw这里：

```xml
<xyz>0 0 1</xyz>
```

所以 yaw 是绕父坐标系的 +Z 转。
ROS 采用右手系：

```text
X 前
Y 左
Z 上
```

从机器人上方往下看：

```text
joint_yaw > 0
```

一般就是逆时针转，也就是向左转。
所以建议你下位机定义：
云台正对底盘 X+ 前方：

```text
joint_yaw = 0

向左转：
joint_yaw > 0

向右转：
joint_yaw < 0
```

例如：

```text
正前方      0 rad
左 90°      +π/2
右 90°      -π/2
后方        ±π
```

这个和 ROS 的右手系最自然。

##### 参数详解

###### use_imu_as_input

use_imu_as_input 决定 IMU 怎样参与滤波。

当前 False 的处理方式是：滤波器内部估计角速度、加速度等状态，收到 IMU 后用测量纠正这些状态，再进行运动预测和激光匹配。

设为 True 后，加速度与角速度作为预测输入，经过单位缩放、偏置处理后推动运动状态。切换模型还会改变所使用的噪声参数，所以首轮保持当前 False。

关闭 IMU 对应的是另一个参数 mapping.imu_en。

###### prop_at_freq_of_imu

prop_at_freq_of_imu 主要影响协方差传播。

协方差可以理解为滤波器对当前估计的不确定程度。当前 True 时，代码在处理 IMU 时刻传播它；状态仍会推进到激光点的采样时刻。

改成 False 后，代码还会在激光逐点时刻增加协方差预测，通常计算量更大。它不是“把 Point-LIO 输出频率设成 IMU 频率”的开关，也不能保证切换后精度更高。

###### check_satu

check_satu 是逐轴处理。

当前代码分别比较三个加速度轴和三个角速度轴：`abs(原始轴值) ≥ 0.99 × 对应饱和阈值`

被标记的轴停止参与这次 IMU 观测更新，其他轴继续使用。因此，它需要配合正确单位和量程的 satu_acc/satu_gyro。这项检查在当前 output 模型中生效。

###### init_map_size

init_map_size=10 只是一道点数门槛。

代码判断的是：`init_feats_world->size() >= init_map_size`

如果一帧预处理后已有几千个点，设置 10 或 100 都可能在同一帧满足条件。因此，增大它不一定增加初始化时间，也不能替代静止 IMU 初始化。

初始化地图使用的是预处理后的点云，并没有直接使用经过 filter_size_surf 体素降采样的那份点云。

三个点数控制参数作用于不同阶段。

初始化完成后的常规处理，大致是：

```text
原始点云
 → line/tag 初筛
 → point_filter_num：按间隔取点
 → 距离等过滤
 → filter_size_surf：扫描空间降采样
 → 逐点匹配
 → filter_size_map：地图插入筛选
```

例如，有约 10,000 个点通过 line/tag 初筛：

- point_filter_num=8：先选择约 1,250 个，后续过滤可能继续减少。
- 改为 4：先选择约 2,500 个。
- 随后扫描体素降采样，还会进一步压缩空间上密集的点。

因此，间隔取点更多，不一定等比例增加最终匹配点数，还要看扫描体素、遮挡和匹配条件。

###### ivox_nearby_type

ivox_nearby_type=18 表示邻接网格类型。

本地实现实际搜索的网格数包含中心网格：

| 配置值 | 搜索范围 | 总网格数 |
|---:|---|---:|
| `0` | 仅中心网格 | 1 |
| `6` | 中心＋面相邻网格 | 7 |
| `18` | 再加入棱相邻网格 | 19 |
| `26` | 再加入角相邻网格 | 27 |

它不表示“找 18 个点”或“搜索 18 米”。

实际空间尺度还取决于 mapping.ivox_grid_resolution，当前为 0.5 m；匹配过程中另有最近邻和残差条件。

以后调这组参数时，主要比较输出延迟、有效环境结构、点云重影和轨迹连续性。先使用当前值建立基准，再针对具体表现改变一个参数，才能判断改善来自哪里。

##### 参数详解

###### lid_topic 与 imu_topic

两个话题参数：名称、消息类型和命名空间必须同时对应。

当前实车驱动设置 xfer_format=4、multi_topic=0，源码发布：

```text
livox/lidar             → Livox CustomMsg
livox/lidar/pointcloud  → PointCloud2
livox/imu              → sensor_msgs/Imu
```

Point-LIO 当前 lidar_type=1，订阅的是 CustomMsg，因此配置中的 livox/lidar 与驱动匹配。

这两个配置都是相对话题名：

| 节点命名空间 | `livox/lidar` 实际解析为 |
|---|---|
| 空命名空间 | `/livox/lidar` |
| `/red_standard_robot1` | `/red_standard_robot1/livox/lidar` |

驱动和 Point-LIO 的命名空间或话题重映射要一致。话题名负责选择输入源，消息中的 frame_id 表示坐标名称；选择话题不会自动进行坐标变换。

###### con_frame 与 con_frame_num

con_frame 的实际行为与注释不完全一致。

当前 Livox 合帧分支执行的是：
1. 收到前10帧，累计它们的点。
2. 把每帧逐点时间调整到第一帧的起始时间。
3. 第11次回调时，把累计点云放入处理队列。
4. 这次回调收到的第11帧没有加入累计点云，然后计数清零。

所以即使设置：

```yaml
con_frame: True
con_frame_num: 1
```

也不会按“合并1帧”执行。代码仍累计10帧，再由下一次回调触发输出。

假设驱动稳定20 Hz，这段逻辑理论上约每11个回调输出一个合并包，即约 1.82 Hz，累计点云覆盖约 0.5秒。这会增加等待时间和单次处理点数，因此首轮保持 False。

###### cut_frame 与 cut_frame_time_interval

拆帧函数存在，但 YAML 开关没有连接到它。

实际代码检查：

```cpp
if (cut_frame_init) 
{
    process_cut_frame_livox(..., cut_frame_num, ...);
}
```

其中 cut_frame_init 默认 False。当前没有发现把 common.cut_frame 赋给它，也没有发现使用 cut_frame_time_interval。
此外，这个内部函数按点数分段，使用 cut_frame_num，并不是直接按照 YAML 中的0.05秒切分。
因此，单独修改这两个 YAML 参数不会实现注释描述的拆帧行为。

###### time_diff_lidar_to_imu

时间差参数没有接入，不代表系统不需要同步。

IMU 回调实际修正时间戳的表达式是：

```text
修正后时间 = 原始时间
           − timediff_imu_wrt_lidar
           − time_lag_IMU_wtr_lidar
```

它使用的是另外两个变量，目前初始化为零；没有使用 common.time_diff_lidar_to_imu。

Point-LIO 仍然会根据时间戳等待 IMU 覆盖点云扫描末尾。但这只是按时间戳组织数据，不能证明两种传感器的物理采样时间已经对齐。

以后实车需要测量实际同步状态；如果发现偏移，必须先确认校正方式及其符号，再处理对应代码或驱动配置。当前把 time_diff_lidar_to_imu 填成非零值，不会完成校正。

##### 参数详解

###### enable

enable 改变的是初始匹配地图的来源。

当前 False 的流程是：

```text
IMU 初始化
 → 累计当前扫描点
 → 达到 init_map_size 门槛
 → 用这些点建立地图
 → 后续匹配并更新地图
```

开启后，达到同样的初始化门槛时，代码改为读取 PCD，并把其中的点加入地图搜索结构。

加载先验地图不会自动完成全局重定位，也不会自动确定机器人在整张地图中的位置。初始位置、姿态和地图坐标必须足够一致，后续局部匹配才有基础。

另外，开启先验后，代码会延后新点插入；相关有效处理计数超过200后，仍会继续更新地图。因此这个开关也不意味着地图永久冻结。

先验 PCD 加载时没有自动做坐标旋转或单位缩放，地图还必须与当前 Point-LIO 参考系一致。源码对 PCD 读取失败返回的空指针也没有在调用处检查，所以启用前需要确认文件有效。

###### prior_pcd_map_path

路径注释只对相应启动链成立。

localization_launch.py 会将启动参数 prior_pcd_file 传给：prior_pcd.prior_pcd_map_path

但它没有因此自动把 prior_pcd.enable 改成 True。当前配置即使获得路径，Point-LIO 仍不加载它。

而 slam_launch.py 会明确覆盖：prior_pcd.enable: False

这与从当前扫描建图的用途一致。

同一定位启动链中的 small_gicp 也会接收先验文件，但它是另一个节点。Point-LIO 关闭先验，不代表 small_gicp 没有使用地图。

###### init_pose

init_pose 有三个容易误解的地方：

- 它是 [x,y,z]，三个数都是米。 第三个数不是 yaw，也不包含 roll/pitch/yaw。
- 它对应内部 IMU 原点在 camera_init 中的位置。 不是直接设置 base_footprint 的导航位置。
- 本地代码的赋值时机比较特殊。 它在首次输出位姿时直接修改 kf_output.x_.pos，并非在加载先验、开始匹配之前统一完成初始化。

尤其在你当前“高频里程计开启、path 关闭”的设置下，这次赋值发生在首次成功匹配后的里程计输出中。因此，未来启用先验时，不能只填一个位置就认为首轮匹配已经从该位置开始；这段初始化顺序需要另行审查。

| 值 | 处理方式 |
|---:|---|
| `1` | Livox CustomMsg；内部名称为 `AVIA`，当前 MID360 也走此路径 |
| `2` | Velodyne 样式 PointCloud2，包含 `time`、`ring` 等字段 |
| `3` | Ouster 样式 PointCloud2，包含 `t`、`ring` 等字段 |
| `4` | Hesai XT32 样式 PointCloud2；原 YAML 注释没有列出这一项 |

它不仅决定字段怎样解析，还决定订阅 CustomMsg 还是 PointCloud2。当前实车驱动在 livox/lidar 发布 CustomMsg，所以设置为 1。

仿真使用 2，是因为转换器生成了 Velodyne 样式字段，并不代表仿真中换了一台 Velodyne 雷达。

###### scan_line

scan_line：限制接受的 line 编号。 当前判断条件是：`msg->points[i].line < N_SCANS`

N_SCANS 来自 scan_line，所以设置4时允许：`line = 0、1、2、3`

本地驱动对 MID360 定义 kLineNumberMid360=4，并按：`point.line = i % pkt.line_num;`生成 line 字段。因此，当前4这个值有驱动代码依据。

例如：
- 改成2：只接受 line 0、1，丢弃 line 2、3。
- 改成8：如果输入仍只有0～3，就不会多出新的点。
它主要是输入格式匹配参数。调节点数密度应首先看前面讲过的 point_filter_num 和体素尺寸。

###### timestamp_unit

timestamp_unit：解释逐点时间字段的单位。 本地枚举及转换关系为：

| 值 | 输入字段单位 | 换算成内部 ms 的倍率 |
|---:|---|---:|
| `0` | 秒，s | ×1000 |
| `1` | 毫秒，ms | ×1 |
| `2` | 微秒，μs | ×0.001 |
| `3` | 纳秒，ns | ×0.000001 |

这个选择在普通 PointCloud2 分支中使用。例如 Velodyne 的 time、Ouster 的 t 会经过相应换算。

但你当前的 Livox CustomMsg 路径直接执行：`curvature = offset_time / 1000000.0;`也就是固定从 ns 转成 ms。因此，当前修改 timestamp_unit 不会改变这条输入路径的时间解释。

举个纯数值例子：

```text
offset_time = 25,000,000 ns
           = 25 ms
           = 0.025 s
```

该点的处理时刻就是：

```text
点云 header.stamp + 0.025 s
```

逐点时间参与运动预测与点云匹配，不能在输入转换中随意丢弃；时间单位换算也不会完成雷达与 IMU 的时差校准。

###### blind

blind：近距离排除半径。 当前代码计算：

\[
r^2=x^2+y^2+z^2
\]

当：

\[
r^2<\texttt{blind}^2
\]

就丢弃该点。因此 blind=0.5 表示排除距离雷达点云坐标原点不足0.5 m的点，范围是一个球形区域。

例如：

- 距离0.3 m的点：被这项过滤排除。
- 距离0.6 m的点：通过距离下限检查，之后仍可能被其他条件排除。

这里的距离是三维距离，与点的高度、机器人中心距离不同。这个过滤同时作用于机器人点和环境点，所以增大它时，也会丢失近处墙面、地面和障碍物的有效点。

实车到位后，先观察0.5 m过滤后是否仍有明显车体干扰、近处有效结构是否不足，再决定是否调整。当前没有这些实测证据，先保持0.5。

##### 参数详解

###### imu_en

imu_en：是否使用 IMU。 当前 True 时，Point-LIO 等待 IMU 覆盖扫描时间，并从初始加速度平均值获得重力方向，后续继续使用惯性信息。它与你前面设置的 use_imu_as_input=False 不冲突：当前是“启用 IMU，并把它作为观测”。

False 会跳过 IMU 初始化与相应同步等待，采用预设重力和雷达约束。你当前有 MID360 内部 IMU，保持 True。

###### extrinsic_est_en

extrinsic_est_en：是否在线估计内部外参。 当前 False 时直接使用配置的 extrinsic_T/R；True 时，激光更新也会尝试修正外参状态。

MID360 雷达与内部 IMU 固定在一起，先使用已知外参。云台 yaw 转动改变的是传感器相对底盘的关系，不会改变这对内部外参，所以不需要因此开启在线估计。

###### imu_time_inte

imu_time_inte：未接入计算的标称间隔。 0.005 s 对应200 Hz的标称周期，但本地只发现声明和读参，没有发现计算用途。实际时间步长来自 IMU 与点云时间戳。修改它不会改变硬件输出频率。

###### lidar_time_inte

lidar_time_inte：回退时间窗口。 正常情况下，扫描末尾是“扫描起始时间＋最大逐点偏移”。这个参数主要出现在失去点云、没有有效点等回退分支中。

因此，驱动发布频率20 Hz与这里填写0.1并不构成直接矛盾。暂时保留，不能只按 1/20=0.05 推断必须修改。

###### satu_acc

satu_acc：加速度逐轴饱和门槛。 当前原始输入采用 g，代码比较：`abs(原始加速度轴值) ≥ 0.99 × 4.0 = 3.96g`
这是逐轴判断，不是判断整个加速度向量的模长。被标记的轴停止参与该次 IMU 观测更新。

原注释“与单位无关”需要纠正：代码直接比较原始数值，阈值必须与输入单位一致。配置4.0表达了约4g的门槛，但实际硬件量程仍需要核对。

###### satu_gyro

角速度逐轴饱和门槛。 当前单位为 rad/s，实际触发值为：`0.99 × 35.0 = 34.65 rad/s`

它与加速度饱和判断一样，在当前 output 模型、check_satu=True 时使用。阈值应对应硬件实际量程，不能用来调整航向漂移。

###### acc_norm

acc_norm：原始加速度单位换算。 实际计算是：

\[
a_{\text{scaled}}
=a_{\text{raw}}\frac{\|\texttt{gravity}\|}{\texttt{acc\_norm}}
\]

你当前 gravity 模长约9.81、acc_norm=1.0，所以原始1g被转换为约9.81 m/s²。
这是单位和比例参数。增大它会减小缩放后的加速度，不能把它作为消除轨迹漂移的调节手段。当前 g 单位输入保持1.0。

###### lidar_meas_cov

lidar_meas_cov：本地实现存在分支不一致。 这里需要修正我此前“调大统一降低激光权重”的概括：那只符合其中一个分支。

令 \(M\) 为一次更新的有效匹配点数，当前 output 模型状态维数为30：
- \(M<30\)：代码将该值加到观测协方差中，按测量方差使用。调大通常降低激光权重。
- \(M\ge30\)：代码在另一种求解公式中直接用它乘 \(H^TH\)，相当于按测量精度使用；调大的权重趋势相反。
同一个参数在两处没有统一为方差或其倒数。

这里的 \(M\) 不是整帧点数：本地按逐点时间分组更新。一帧有几千个点，不代表必然进入后一分支。源码公式的不一致可以确认；实车是否触发、触发频率及实际影响尚未验证。 当前先保持0.01，不据此盲调或修改源码。

噪声参数继续往下看之前，需要区分两种量：
- 测量噪声 \(R\)：描述对一次观测的不确定程度。增大通常降低对该观测的信任。
- 过程噪声 \(Q\)：描述预测过程中状态的不确定程度增长。增大使相关状态更容易被观测修正。
本地过程协方差使用：
\[
P_{\text{new}}=FPF^T+Q\,dt^2
\]
因此，下面过程噪声的单位按“乘以秒²后成为对应状态方差”推导，不能直接当成原始测量方差或常见的每根号 Hz 噪声密度。

###### acc_cov_output

acc_cov_output：加速度状态过程噪声。 当前 output 模型把加速度作为状态。500表示它的过程不确定度系数，单位按本地公式为 m²/s⁶。

例如，若协方差预测步长恰好为0.005秒，该项增加的加速度状态方差为：
\[
500\times0.005^2=0.0125\;(\mathrm{m/s^2})^2
\]
它不会直接给机器人添加“500的加速度”；改变的是滤波器对状态的信任程度。

###### gyr_cov_output

gyr_cov_output：角速度状态过程噪声。 与上一项对应，作用于角速度状态。增大允许观测更明显地修正角速度；减小使预测更相信角速度保持原来的趋势。1000是过程系数，不是陀螺仪的真实测量方差。

###### b_acc_cov

b_acc_cov：加速度偏置变化的过程噪声。 加速度偏置会与加速度状态共同解释 IMU 测量。增大允许偏置更快变化，过大时可能使偏置吸收本应由真实运动解释的变化；减小则适应漂移更慢。当前先保持0.0001。

###### b_gyr_cov

b_gyr_cov：陀螺偏置变化的过程噪声。 作用方式与加速度偏置类似。它影响滤波器允许陀螺零偏怎样演变，不能单独凭“航向有漂移”就认定应该增大。

###### imu_meas_acc_cov

imu_meas_acc_cov：加速度观测测量噪声。 当前残差是：
\[
r_a=a_{\text{scaled}}-a_{\text{state}}-b_a
\]
所以0.1作用于缩放后的米制加速度观测。按方差理解，其数值对应标准差约0.316 m/s²；这是滤波器赋予的噪声，不代表已经实测出传感器有这个标准差。

###### imu_meas_omg_cov

imu_meas_omg_cov：角速度观测测量噪声。 当前残差是：
\[
r_\omega=\omega_{\text{raw}}-\omega_{\text{state}}-b_g
\]
单位为 rad²/s²。增大降低 IMU 角速度观测的权重，减小则更相信它，也更容易受到测量噪声和振动影响。

###### gyr_cov_input

gyr_cov_input：input 模型角速度输入噪声。 它进入 input 模型的过程噪声矩阵，当前 use_imu_as_input=False 不使用这项进行实际预测。此时修改它，不会改变当前模型的角速度权重。

###### acc_cov_input

acc_cov_input：input 模型加速度输入噪声。 同样在切换到 use_imu_as_input=True 后才参与对应预测。该模型仍会把原始加速度转换到 m/s²，因此这里按米制加速度噪声理解。

###### plane_thr

plane_thr：地图邻域是否足够平整。 代码先找5个地图邻点，拟合平面，再检查这5个点到拟合平面的距离。只要有一个超过0.1 m，就不接受这个邻域作为平面。
这项检查的是地图邻点自身能否构成平面。增大更宽松，减小更严格。

###### match_s

match_s：当前点能否匹配这个平面。 地图邻域通过平面检查后，再判断：
\[
r>s\,d^2
\quad\Longleftrightarrow\quad
|d|<\sqrt{r/s}
\]
其中：
- \(r\)：当前雷达点距雷达原点的距离，m；
- \(d\)：当前变换后点到地图平面的残差，m；
- \(s\)：match_s。

因此，按米制长度判据，match_s 隐含单位为 m⁻¹。当前81对应：

| 点距离 \(r\) | 残差上限 \(\sqrt{r/81}\) |
|---:|---:|
| 1 m | 约0.111 m |
| 4 m | 约0.222 m |
| 9 m | 约0.333 m |

增大 match_s 会更严格。它与 plane_thr 检查的对象不同：前者检查当前点的匹配残差，后者检查地图邻域的平整程度。

###### ivox_grid_resolution

ivox_grid_resolution：地图搜索索引网格。 当前把地图空间分成边长0.5 m的网格，匹配时根据 ivox_nearby_type=18 检索中心及邻接网格中的点。
它与前面两个0.2 m参数作用不同：

filter_size_surf        → 当前扫描降采样
filter_size_map         → 地图插入筛选
ivox_grid_resolution   → 地图搜索索引

这里增大网格不会自动减少点数。单格内可能装入更多点，因此搜索不一定更快；减小则可能让固定邻域覆盖的物理范围不足。

###### gravity与gravity_init

gravity：目标参考系重力，以及输入缩放大小。 它同时用于：
1. 初始化 camera_init 中的重力状态；
2. 用其方向对齐初始 IMU 姿态；
3. 用其模长设置 G_m_s2，参与原始加速度缩放。

gravity_init：初始 IMU 系中的预设重力。 当前 imu_en=True 时不读取它，而是计算：
\[
g_{I_0}=-\frac{\overline a}{\|\overline a\|}G
\]
imu_en=False 时才使用预设向量进行初始姿态对齐。
再补充一个细节：本地对齐函数主要使用这个向量的方向，同方向等比例缩放不会改变对齐旋转；真正决定 G_m_s2 的是 gravity。将 gravity_init 写成约9.81的米制物理向量，是保持参数含义一致。

咱们的mid360是roll = -π/4 = -45°安装的。

方法一：理论计算法（适用于实物和仿真）

机器人静止时，IMU 的 linear_acceleration 本质上测的是与重力反向的“比力”。如果只绕 X 轴 roll 一个角度 r，那么静止时大致有：

```text
ax = 0
ay = g·sin(r)
az = g·cos(r)
```


```text
g = 9.81 m/s²
r = -45°


ax = 0

ay = 9.81 × sin(-45°)
   ≈ -6.9367

az = 9.81 × cos(-45°)
   ≈ +6.9367
```

tmp_gravity =
    -mean_acc / mean_acc.norm() * G_m_s2;

G_m_s2 ≈ 1.0 g ≈ 9.81 m/s²（在point_lio源码中用的是m/s²）

###### extrinsic_R

extrinsic_R：雷达向量到内部 IMU 系的旋转。 当前单位矩阵表示两者轴向一致。即使整台 MID360 倾斜安装，也可以继续使用单位矩阵，因为雷达与内部 IMU 一起倾斜。

##### 参数详解

###### publish_odometry_without_downsample

这个开关控制里程计输出的节拍：

- True：每次成功的逐点／时间组匹配后发布，时间戳为当前采样时刻，输出更密集，实际频率取决于成功更新次数。
- False：每帧处理结束后发布一次，时间戳为扫描末尾；输入20 Hz且每帧正常处理时，通常约20 Hz输出。

当前先保持 True。后续若输出和接收负载过高，再考虑 False；改变的是输出节拍，逐点估计与点云降采样仍然执行。

##### 参数详解

###### path_en

True 时发布 path 累计轨迹，方便在 RViz 中观察机器人传感器的运动路线；False 时关闭该轨迹输出，里程计仍照常发布。

观察 SLAM 轨迹时可以按需开启。轨迹没有固定长度上限，长时间累计会增加内存和显示负担。

###### scan_publish_en

当前保持 True，发布 cloud_registered 配准扫描，供 RViz 和后续接口使用。

False 时关闭当前配准扫描及依赖它的 body 点云输出，内部估计和建图仍继续。原注释“关闭全部点云输出”不完全准确：初始化的 Laser_map 仍可发布。另外，本地 PCD 保存所需的点云累计也放在这个分支内，后续启用保存时应保持 True。

###### scan_bodyframe_pub_en

True 时额外发布 cloud_registered_body，将预处理点云通过内部外参转换到 IMU 坐标系，主要用于辅助检查点云和外参；需要 scan_publish_en 同时为 True。

这里的 body 指 MID360 内部 IMU 坐标系。当前没有这项调试需求，先保持 False。

###### tf_send_en

True 时随里程计发布 camera_init → aft_mapped 的 TF；False 时关闭这条 TF，里程计和配准扫描仍可继续输出。

当前集成链先保持 False，底盘 TF 由其他接口节点发布。单独调试需要显示 Point-LIO 自身位姿 TF 时，再考虑开启；这条 TF 表达内部 IMU 位姿，不是 odom → base_footprint。

#### pcd_save

##### 参数表

```yaml
    pcd_save:
      pcd_save_en: False
      interval: -1                                      # how many LiDAR frames saved in each pcd file;
                                                        # -1 : all frames will be saved in ONE pcd file, may lead to memory crash when having too much frames.
```

| 参数名 | 当前值 | 单位 | 实车处理建议 | 作用 | 调大效果 | 调小效果 | 生效条件／备注 |
|---|---|---|---|---|---|---|---|
| `pcd_save_en` | `False` | 不适用，布尔 | **根据实际功能需求开启或设置** | 是否累计并保存配准扫描为 PCD 文件 | 不适用 | 不适用 | 本地累计点云需 scan_publish_en=True；集成 SLAM launch 会覆盖为 True |
| `interval` | `-1` | 次，扫描处理计数；-1为特殊值 | **根据实际功能需求开启或设置** | 控制每累计多少次扫描处理后保存一份文件 | 正数范围内：保存间隔更长，单文件通常更大、缓存更多 | 正数范围内：保存更频繁，单文件通常更小、写盘次数更多 | -1：累计到正常退出再保存；大于0：分批保存并清空累计缓存；不是秒；仅实际保存开启时生效，集成 SLAM launch 会开启保存 |

##### 参数详解

###### pcd_save_en

False 时关闭 PCD 保存，估计和建图仍继续；True 时累计 camera_init 坐标系中的配准扫描，保存为二进制 PCD。

当前先保持 False，需要存档时再开启，并保持 publish.scan_publish_en=True。注意：slam_launch.py 会把该参数覆盖为 True，所以是否保存还要看实际启动方式。

###### interval

- -1：持续累计点云，正常退出时保存到 scans.pcd。长时间运行会增加内存占用，需要正常结束程序才能执行退出保存。
- 大于0：每累计指定次数的扫描处理就保存为 scans_1.pcd、scans_2.pcd 等，并清空累计缓存；正常退出时，剩余点仍保存到 scans.pcd。

这个计数按进入保存分支的扫描处理次数增加。例如稳定20 Hz且每帧正常处理时，100次约为5秒，但 interval 本身不是时间参数。本地仅在 interval>0 时分批保存，0及其他负值也不会触发周期保存，使用默认特殊值 -1 更清楚。

当前编译的默认输出目录为：

```text
/src/pb2025_sentry_nav/point_lio/PCD/
```

保存内容是多帧配准扫描的累计点云；文件不会自动放到导航先验地图目录。输出文件名固定，需保留不同轮次结果时，应先归档已有文件。
